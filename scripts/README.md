# Below the Last Lantern — Scripts Reference

Tests for these scripts live in `res://tests/`. See `res://tests/README.md` for conventions.

## Core Scripts (`res://scripts/`)

### GridCell.gd
**Type:** Resource (data only, not attached to a node)
**Purpose:** Represents a single tile in the dungeon grid. Stores the cell type (WALL, FLOOR, ENTRANCE, EXIT), wall flags for each side (north/south/east/west), an optional `object: ObjectInstance` (chest, door, etc. — null when empty), an optional `trap: TrapInstance` (separate slot from `object` so a chest never collides with a trap on the same tile — placement enforces "trap OR object, not both"), an optional `spinner: SpinnerInstance` (Phase 8 Task 8 — third parallel slot; placement enforces a spinner never shares a cell with a trap, chest, lever, projectile-trap pressure plate, or floor item), an optional `teleporter: TeleporterInstance` (Phase 15 Task 6 — fourth parallel slot; both endpoints of a pair point to the SAME instance, resolve the destination via `inst.partner_of(cell)`), an optional `scenery: SceneryInstance` (fifth parallel slot — trees / flowers / mushrooms placed by `_place_scenery()`; mutual exclusion against every other special-content slot is enforced by the placer), and an `items: Array[ItemInstance]` for items piled on this tile. The `is_blocked` property returns true if the cell is a wall OR if it holds an object whose `data.blocks_movement` is true OR if it holds non-walkable scenery (a tree). Traps, spinners, teleporters, and WALKABLE scenery (flowers) NEVER block — they live in their own slots and exist to be walked onto / through.

### LevelGenerator.gd
**Type:** Node
**Purpose:** Procedurally generates dungeon levels using a Growing Tree maze algorithm. Creates a 2D grid of GridCell resources, carves corridors with configurable wiggle and width variation, optionally places rooms, connects all regions, places entrance/exit points, then in order: cell-bound objects (chests etc.), edge-bound doors, lever ↔ door M:N clusters, **key ↔ locked-door pairs (Phase 8 Task 2c)**, **traps (Phase 8 Task 3 — Subtask A scattered + Subtask B1 corridor clusters)**, floor items, and finally wall decorations (paintings, torches, lanterns). Traps are placed AFTER all object passes (so trap cells are guaranteed free of chests / doors / levers) and BEFORE items (so loot doesn't pile on a hazard the player would have to step on); traps don't block movement so they don't affect chain reachability — no BFS validation needed at this layer. **Subtask B3 post-placement validators** run after all trap passes: (1) `_validate_chest_lever_timed_adjacency()` scans every chest/lever cell and ensures at least one 4-adjacent walkable cell is free of TIMED traps (step traps adjacent are OK — they're one-shot); if none exists, one timed trap is removed from a neighbour via `_remove_trap_at(pos)`. (2) `_validate_timed_trap_safe_distance()` enforces `room_max_distance_to_safe_cell` globally (not just within rooms during placement) — corridor clusters meeting room edges can create long timed-trap runs that exceed the per-room guarantee; this pass removes timed traps until every walkable cell has a non-timed-trap walkable cell within K tiles. (3) `_validate_step_trap_reachability()` runs Dijkstra from entrance to ALL reachable cells (step-trap cells cost 100, regular cells cost 1, blocking objects/walls impassable, doors passable), then traces cheapest paths to exit + every chest (via adjacent cell) + every lever + every floor-item cell and removes every step trap along those paths in one batch — guaranteeing damage-free routes while preserving density (~30 removals on a 200+ trap level). Runs AFTER `_place_items()` so floor-item positions are known. `_remove_trap_at(pos)` is the single entry point for trap removal: clears `cell.trap`, removes from the `traps` flat list, and removes from `_cluster_cells` if present. All three trap candidate filters (`_eligible_segment_cells`, `_eligible_room_cells`, `_trap_candidates_for_spawn`) also skip cells that already hold floor items (floor keys from `_place_key_doors` land before traps). **Trap placement runs in three passes per spawn**: first a corridor-cluster pass (when `TrapSpawn.uses_corridor_clusters()`) lays contiguous runs of N trap cells inside chosen corridor segments; then a room-density pass (when `TrapSpawn.uses_room_density()`) places traps inside rooms at a target coverage percentage with optional Manhattan spacing; finally the legacy scattered pass lays `count_min..count_max` individual traps with a distance preference. The cluster pass uses `_detect_corridor_segments()` — a connected-components scan over corridor-classified cells that excludes "junctions" (corridor cells with 3+ corridor neighbours) so two corridors meeting at a T don't merge into one giant segment. Two segment-skip rules govern cross-spawn / cross-segment placement: a segment is rejected if it already holds traps OR if it is junction-adjacent to a trapped segment (otherwise two clusters separated only by a non-trappable junction read as one long run with a single safe tile in the middle, forcing more damage than the per-segment max would suggest). Cluster cells are tracked in `_cluster_cells: Dictionary` and the scattered pass excludes any candidate that's 4-adjacent to a cluster cell — without this exclusion, a 5-cell segment with a 3-cell cluster leaves the 2 leftover cells eligible for scattered, producing a 5-trap contiguous run that defeats the per-segment cluster cap. The room pass iterates `_room_rects`, rolls `room_chance` per room, and places traps respecting `room_min_spacing` against any existing trap in the SAME room (cross-spawn so two spawns sharing a room don't oversaturate). `allow_mixed_room_traps = false` opts a spawn out of sharing — analogous to the one-spawn-per-segment rule for corridor clusters. Object placement runs after BFS validation with a per-placement reachability check (each blocking object must keep every floor cell reachable from the entrance AND every blocked-but-walkable-adjacent object reachable too — if not, the object is rolled back and a different cell is tried). Door placement: doors live on EDGES (between two adjacent floor cells) — never on a `GridCell` — and are stored exclusively in `LevelGenerator.doors`. Doors only land on edges where both endpoints are 1-cell-wide-corridor cells (exactly 2 non-wall neighbours; straight or bend), neither is entrance/exit, and neither holds a chest. Decorative doors (`ObjectSpawn.must_gate_content = false`) need no extra reachability check because open doors don't block and closed doors are always re-openable. **M:N cluster placement** (lever ↔ door) runs after decorative doors. Each cluster produces N doors then M levers, all cross-linked. Doors are placed first; levers are spread via farthest-first heuristic with one-lever-per-room uniqueness. Distance constraints (`lever_to_door_min/max_distance`) degrade gracefully (~30 inner attempts before relaxing). The entire cluster is validated by **chain reachability**: starting at the entrance with directly-clickable non-lever-locked doors treated as open, the simulator iteratively collects reachable levers then evaluates each lever-locked door under its AND/OR logic (AND: all linked levers reachable → door opens; OR: any one → door opens) until fixed point. Lever-locked doors are excluded from the initial open-set regardless of `interactable`. A cluster is only accepted if no previously chain-reachable cell becomes unreachable AND all cluster levers have reachable neighbours. If `door_must_gate_content` is true, at least one cluster door must gate content. Failure rolls back the ENTIRE cluster (all doors + all levers) atomically. **Chain reachability v2** (Phase 8 Task 2c) extends the simulator to also collect keys and unlock matching doors during the iteration. Key-door placement uses the same accept-or-rollback model with floor/chest fallback locations; `must_gate_content=true` (the default for key-doors) additionally rejects placements where the locked door doesn't actually gate any chest, lever, key, or exit cell. Item placement skips cells already occupied by a blocking object. All generation parameters are read from a `BiomeData` resource via `configure(biome)`. Exposes `classify_cell(pos) → int` (returns one of the `ObjectSpawn.PLACEMENT_*` constants — Corridor / Room / Dead End) so DungeonView can pick texture variants per cell type.
**Key state:** `doors: Array[DoorInstance]`, `_doors_by_edge: Dictionary` (internal index), `linked_objects_pool: Array[LinkedObjectSpawn]`, `wall_switches: Array[WallSwitchInstance]` (sibling to lever-door pairs — switches are wall-face anchored, NOT cell-bound; populated by `_place_wall_switched_doors()` after lever-door clusters and before key-doors; cross-linked with `DoorInstance.linked_wall_switches` so a click on the switch toggles every linked door and a door toggle refreshes every back-linked switch's sprite), `wall_decorations: Array[WallDecorationInstance]`, `_wall_faces_used: Dictionary` (face_key → true so two decos / projectile launchers never share the same wall face — same registry covers both systems), `traps: Array[TrapInstance]` (flat list of all placed traps so Game.gd can iterate without re-scanning the grid each frame; mirrors `cell.trap` per-cell lookups), `projectile_traps: Array[ProjectileTrapInstance]` (Phase 8 Task 3 — Subtask C; wall-mounted launchers placed by `_place_projectile_traps()` after spike-trap validators and before wall decorations so the shared `_wall_faces_used` registry blocks decorations from claiming a launcher's face), `projectiles: Array[ProjectileInstance]` (in-flight projectiles spawned by TIMED launcher tick rollovers; Game.gd advances every entry each frame via `_tick_projectiles` and removes those that hit a wall; cleared in `generate()` so a level transition starts with an empty list), `spinners: Array[SpinnerInstance]` (Phase 8 Task 8; floor-cell spinners placed by `_place_spinners()` after projectile traps and before wall decorations — last among floor passes so the placer knows every exclusion (chests/levers via `cell.object`, traps via `cell.trap`, items via `cell.items`, projectile-trap pressure plates collected from `projectile_traps`). Mirrors `cell.spinner` per-cell lookups so renderer + Game.gd trigger logic iterate without re-scanning the grid each frame.), `_spinner_cluster_cells: Dictionary` (subset of spinner cells produced by the corridor-cluster pass — scattered placements use this to avoid 4-adjacency, mirroring `_cluster_cells` for traps)
**Key methods:** configure(biome: BiomeData), generate(), get_door_at_edge(a, b) → DoorInstance, is_edge_blocked(a, b) → bool, get_secret_wall_at_edge(a, b) → SecretWallInstance, get_wall_switch_at(view_cell, view_side) → WallSwitchInstance (renderer + map drawing — returns null when no switch is on the given face), classify_cell(pos: Vector2i) → int, classify_wall_face(pos: Vector2i, wall_dir: Vector2i) → int (mostly mirrors `classify_cell`; at a dead-end cell only the BACK wall — the one facing the player walking in — keeps `PLACEMENT_DEAD_END`, side walls fall back to `PLACEMENT_CORRIDOR` so a dead-end-only texture lands once in front rather than wrapping the cell on three sides)

**Wall-switched door placement.** `_place_wall_switched_doors()` runs after `_place_linked_objects()` and before `_place_key_doors()`. For each `WallSwitchedDoorSpawn` the placer attempts `count_min..count_max` pairs; each pair places a door on a 1-wide-corridor edge (same eligibility as decorative + lever-locked doors via `_candidate_edges_for_door_object`) AND a wall switch on a wall face whose Manhattan distance to either door endpoint lands in `[min_wall_distance, max_wall_distance]`. Switch candidates are bucketed by distance and picked uniformly across non-empty buckets (so `max = 0` always lands on the door panel, `min = 0, max = 1` flips 50/50 between on-door and adjacent wall, etc.). For distance 0 the placer emits two candidates per door — one from each endpoint, view_side pointing across the door's edge. For distance > 0 the placer iterates every floor cell within range whose `view_side` faces a real WALL cell; cells that would float on an internal floor↔floor boundary are rejected. The `along_offset` is rolled per placement: an absolute magnitude in `[along_offset_min, along_offset_max]` then a random sign (50/50 left/right of the wall face's centre). Each tentative pair validates via `_wall_switch_chain_ok`: `_chain_reachable_from_entrance` extended so wall-switched doors are excluded from the auto-open set initially AND promoted to openable once any linked switch's view cell is reachable (mirrors the lever fixed-point loop). The pair is committed only when every pre-pair-reachable cell stays reachable AND the switch's view cell itself is reachable (otherwise the player can never click the switch). `door_must_gate_content = true` adds a `_door_gates_content` check; any failure rolls the door + switch back atomically — no orphan halves. The cross-link (`door.linked_wall_switches.append(sw)` / `sw.linked_doors = [door]`) is the runtime hook Game.gd's click handler uses to flip every linked door on a switch click, and the renderer (DungeonView) uses to refresh switch sprites after the door toggles.

**Secret-wall placement.** `_place_secret_walls()` runs after `_place_spinners()` and before `_place_wall_decorations()` — late enough that floor items are placed (so `gate_mode = LOOT_ONLY` can verify a floor item becomes unreachable when the edge is sealed). Each spawn produces `count_min..count_max` instances; for each, `_try_place_secret_wall` shuffles candidate edges (1-wide corridor on both ends, no entrance/exit, no chest underneath — same as doors) and commits the first one that (a) doesn't already host a door or another secret wall, and (b) satisfies the configured gate mode under `_secret_wall_gates_content`. The gate check feeds the secret-wall edge_key through `_chain_reachable_from_entrance({}, extra_closed_edges)` — `_bfs_with_doors_state` merges `extra_closed_edges` into its `closed_edges` set, so the BFS treats the corridor edge as a permanent wall. All non-NONE placements share a BRIDGE rule: sealing the secret-wall edge must disconnect at least one of its endpoints from the entrance. If both endpoints stay reachable via other paths, the wall sits on a loop and walking through reveals nothing the player couldn't have reached otherwise — the placement is rejected. On top of that, ANY_CONTENT passes when ANY chest / lever / key / exit / floor-item cell becomes unreachable. LOOT_ONLY passes only when a chest OR non-key floor item becomes unreachable AND NO progression cell (exit, lever, floor key, chest-held key) does — a wall that gates "loot AND the exit" is rejected. A `push_error` runtime check at commit time guards the bridge invariant — if a future regression in `_chain_reachable_from_entrance` ever lets a loop edge slip through, the log will scream rather than silently shipping a useless secret wall. Secret walls are NEVER added to `_doors_by_edge`, NEVER block `is_edge_blocked`, and NEVER appear in `GridCell.object` — `PlayerController._step` and the regular reachability BFS ignore them entirely. The illusion is wired in DungeonView (extra wall quads on the edge), MapPopup (faint wall line on the edge — same geometry as real walls, alpha multiplied by `SECRET_WALL_MAP_ALPHA`), and MapData (`reveal_around` skips the orthogonal cell behind a secret wall + the two adjacent diagonals so the corridor continuation stays hidden until the player traverses).

**Projectile-trap placement (Phase 8 Task 3 — Subtask C):** `_place_projectile_traps()` runs after spike-trap validators and before `_place_wall_decorations()`. For each `ProjectileTrapSpawn` it dispatches an additive pair of passes: corridor placement (Subtask C1) when `uses_corridor()` and placement allows corridors, and room placement (Subtask C5) when `uses_room()` and placement allows rooms. Both passes write into the same registries (`projectile_traps` flat list, `_wall_faces_used`, `_projectile_path_cells`) so cross-pass constraints (wall-face exclusivity vs. decorations, path overlap, spreading) hold across both.

**Corridor pass — `_place_corridor_projectile_traps()`** iterates corridor segments (reusing `_detect_corridor_segments()`) and rolls `corridor_chance` per segment. **Cross-spawn segment cap:** before rolling, `_segment_has_projectile_trap(segment)` rejects any segment that already holds a launcher from a prior spawn — fast short-circuit for the common case (the path-overlap rule below would catch same-segment placements anyway, but this avoids re-tracing every wall face inside an already-trapped segment). **Path validation:** for each candidate `_projectile_launch_path(cell, wall_dir, junctions, max_escape)` walks the FULL projectile flight (from `cell + fire_direction` until it hits a wall) and returns the path on success / an empty array on rejection. Validity rules: (a) `cell + wall_dir` is a WALL (mount point), (b) every cell on the path is a corridor FLOOR (no rooms — junctions count as corridor), (c) no cell on the path is the EXIT or holds a CHEST or LEVER object, (d) at least one cell on the path within `max_escape_distance` is a junction (corridor cell with 3+ corridor neighbours) — the player's escape route, (e) **no cell on the path is on another launcher's projectile path** (no crossfire). Junctions come from `_detect_corridor_junctions()` (computed once per generation). Per-spawn cap = `corridor_max_per_segment`.

**Room pass — `_place_room_projectile_traps()`** iterates `_room_rects` and rolls `room_chance` per room. **Path validation:** `_projectile_launch_path_in_room(cell, wall_dir, room)` mirrors the corridor path validator but enforces `room.has_point(npos)` on every path cell — the FULL projectile flight must stay inside the same room rect. Escaping through a doorway into a corridor (or an adjacent room) makes the projectile unavoidable outside the controlled space, so any leak rejects the candidate. Chest/lever/exit/path-overlap fairness rules are reused; the junction-reachability rule is dropped (rooms have no junctions in the corridor sense, and the player's escape is sidestepping inside the room or stepping out through a doorway). Per-room cap = `room_max_per_room`. PRESSURE_PLATE plate placement for room launchers calls `_pick_plate_cell_for_room(path, launcher_cell, data)`, which keeps the "on path" + "≥ `min_plate_to_launcher_distance`" rules and drops the `max_plate_to_junction_distance` constraint (no junctions to measure against). A PRESSURE_PLATE room launcher that can't satisfy the relaxed plate rules is still rejected — no inert plates.

**Shared registries.** The placer maintains `_projectile_path_cells: Dictionary` (Vector2i → true) of every cell on every placed launcher's path; new candidates are rejected via `_path_overlaps_existing(path)` and committed paths are added on placement (re-run just before commit because earlier candidates in the same loop iteration may have laid down paths that now overlap). Spreading is enforced via `_too_close_to_existing_projectile_trap(pos, min_distance)` against ALL prior placements regardless of pass; no graceful degrade — a candidate that violates spacing is skipped. Wall-face exclusivity uses `_wall_faces_used` (`ProjectileTrapInstance.face_key` matches `WallDecorationInstance.face_key` exactly so the registry covers both systems, across both passes).

**Spinner placement (Phase 8 Task 8):** `_place_spinners()` runs AFTER `_place_projectile_traps()` so the placer can collect every projectile-trap pressure-plate cell via `_gather_plate_cells()` and exclude them, and BEFORE `_place_wall_decorations()` (wall decorations don't share cells with spinners but the ordering keeps the floor-pass / wall-pass separation clean). Mirrors `_place_traps` exactly — three additive modes per spawn: a corridor-cluster pass when `SpinnerSpawn.uses_corridor_clusters()` (reuses `_detect_corridor_segments` + `_gather_run_in_segment` from the trap pass), a room-density pass when `SpinnerSpawn.uses_room_density()` (rolls coverage percentage, places spinners respecting `room_min_spacing`), and a scattered pass with `count_min..count_max` placements + graceful-degrade on `min_distance_to_other_spinner`. `_classify_spinner_candidate_cells(plate_cells)` builds the candidate pool: classifies by `_is_dead_end` / `_is_in_room` / corridor and excludes entrance / exit / `cell.object` (chests, levers) / `cell.trap` / existing `cell.spinner` / non-empty `cell.items` / plate cells. `_commit_spinner_at` rolls the instance's fixed `rotations` (in `[data.min_spins, data.max_spins]`) and `direction` (`_roll_spinner_direction` collapses `SpinnerData.Direction.RANDOM` to a concrete CW or CCW via the seeded RNG) once at placement and stores them on the `SpinnerInstance` — every future trigger of this spinner uses those locked values.

**Teleporter placement (Phase 15 Task 6).** Two MUTUALLY EXCLUSIVE modes share `BiomeData.teleporter_spawn`; the predicate `TeleporterSpawn.uses_partition()` (true iff `island_count_max >= 2`) selects between them.

**Phase A (shortcut) mode** — `_place_teleporters()` runs AFTER `_place_secret_walls()` and BEFORE `_place_wall_decorations()` (last among floor passes). Places `count_min..count_max` independent pairs on random non-special floor cells. Early-exits when `uses_partition()` is true so Phase A and Phase C don't double-place. `_gather_teleporter_excluded_cells()` collects every hard-exclusion cell: entrance / exit / `cell.object` (chests + levers) / `cell.trap` / `cell.spinner` / non-empty `cell.items` / door endpoint cells (both, since doors are edge-bound) / projectile-trap plate cells. `_try_place_teleporter_pair()` builds the candidate pool with graceful-degrade on `min_distance_to_other_object` AND `min_distance_to_other_teleporter`, picks endpoint A, then graceful-degrades on `min_distance_between_partners` for endpoint B. Both endpoints share the SAME `TeleporterInstance` so `inst.partner_of(cell)` resolves the destination from either side. `pair_index` is assigned sequentially (0, 1, 2…) so MapPopup's per-pair hue rotation produces stable colours. `get_teleporter_at(cell) -> TeleporterInstance` is the per-cell lookup Game.gd uses to trigger the warp.

**Phase C (island topology) mode** — `_partition_and_place_teleporters_if_enabled()` runs FIRST (right after `_validate_path()`, BEFORE every object / door / trap / item / spinner / secret-wall pass) so the partitioned topology is visible to every downstream placement. K is rolled in `[island_count_min, island_count_max]` (clamped to ≥ 2). The outer `_try_partition_attempt()` retry loop (up to `_PARTITION_OUTER_ATTEMPTS = 8`) reseeds seal candidates on each attempt so a tight-island pick doesn't permanently kill the level. Each attempt:
1. **`_pick_seal_cells(K-1, spawn)`** is QUALITY-DRIVEN, not random — a naive greedy picker happily strands a 2-cell dead-end stub, leaving the warp on nothing for the player to do. Each iteration calls `_score_seal_candidates` (filters by `_is_door_endpoint`, distance-to-entrance/exit, distance-to-previous-seals, articulation, AND `min_island_size` floor via `_smaller_component_size_if_sealed`) and sorts the survivors descending by smaller-component size (largest first = most balanced split). The pick is uniform-random in the top quartile so seeds vary without losing the balance bias. Each pick is evaluated against the CURRENT (post-previous-seals) grid so K=3+ articulation is checked incrementally. Seals are temporarily applied during the scan then rolled back — the outer pipeline owns the atomic commit so rollback paths only have to undo one layer of state.
2. **`_is_articulation_cell(pos)`** runs `_bfs_walkable_skipping(entrance_pos, {pos})` and compares the visited count against the total non-wall cells (minus pos). O(V) per call × O(pool) candidates = O(V²) total — well under a millisecond on a 21×21 grid.
3. **`_identify_islands()`** flood-fills the post-seal grid into a `[islands × cells]` array. Defensive guard: if the count doesn't equal K, rollback and let the outer loop retry.
4. **`_spanning_tree_of_islands(islands, entrance_island)`** greedily connects each unvisited island to the closest visited one (`_islands_closest_distance` = min Manhattan between any pair of cells). Produces exactly K-1 edges rooted at the entrance's island by induction.
5. **`_place_teleporter_pair_across_islands`** drops one endpoint per island per tree edge via `_filter_island_for_teleporter` (entrance/exit + non-empty content filter) + graceful-degrade on `min_distance_between_partners`. Pair count is `K-1` — `count_min/count_max` are IGNORED in this mode.
6. **Final validation** — `_chain_reachable_from_entrance()` must include `exit_pos`. Chain reachability v3 makes this the proof that the spanning tree is correct.

Any failure (no articulation candidates, island count off, pair placement fails, chain v3 loses the exit) triggers `_rollback_partition`: restores every sealed cell to FLOOR and clears placed teleporters back to the snapshot. The outer loop retries; if all 8 attempts fail, the level ships flat (no partition, no teleporters) with a `push_warning` — a flat level is fine, a broken one isn't.

**Chain reachability v3 (Phase 15 Task 6 — Phase C):** extends `_chain_reachable_from_entrance` / `_bfs_with_doors_state` / `_bfs_walkable_with_closed_edges` to thread an optional `teleporter_links: Dictionary` (Vector2i → Vector2i, bidirectional). The top-level call builds the dict from `self.teleporters` via `_build_teleporter_links()`; the BFS enqueues the partner whenever it visits a teleporter endpoint, modelling pairs as permission-free bidirectional graph edges. Empty dict = legacy behaviour, so Phase A levels and pre-Phase C tests pass unchanged. Every existing caller (linked-object placement, key-door placement, secret-wall gating) transparently gets island-aware reachability — a key on island B is chain-reachable iff entrance → corridors → warp → island B → ... → key resolves, so locked-door / lever puzzles still validate correctly across the seal.

**Downstream co-location guards (Phase 15 Task 6 — Phase C):** every placement-pass candidate filter excludes cells with `cell.teleporter != null`: `_is_door_endpoint` (doors + secret walls), `_classify_floor_cells` (objects + items + traps), `_eligible_segment_cells` + `_eligible_room_cells` + `_trap_candidates_for_spawn` (the three trap candidate paths), `_classify_spinner_candidate_cells` (spinners), `_pick_plate_cell_for_room` + `_pick_plate_cell_for_corridor` (projectile-trap plates). Without these guards, a chest / item / trap / plate / spinner could land on a rune circle and visually overlap or step-trigger something the player can't make sense of.

**Outdoor-mode filler placement.** `_place_fillers()` runs LAST in the pipeline, after `_place_wall_decorations()`. No-op when `outdoor_mode = false` or `filler_spawns_pool` is empty. For each `FillerSpawn` it iterates every cell in `[-border_ring_depth, grid_width + border_ring_depth) × [-border_ring_depth, grid_height + border_ring_depth)`, filters via `_is_filler_cell(pos)` (true for out-of-grid cells and in-grid WALL cells; false for FLOOR / ENTRANCE / EXIT), samples a per-cell density, picks a sprite uniformly from the pool, jitters within `jitter_radius` of cell centre, and appends a `FillerInstance`. **Front-row bias:** before each placement the per-cell `_floor_neighbour_direction(pos)` is computed once and shared across every filler in that cell. When non-zero AND `spawn.front_row_bias > 0`, the random offset is lerped toward `floor_dir × _FILLER_FRONT_ROW_EDGE` (= 0.45, just inside the cell to avoid seam-stitching with the adjacent cell's sprites). The result: sprites in WALL cells that border a FLOOR cell cluster at the floor-adjacent edge, marking the wall line so the player can read where they can / can't walk. Interior WALL cells (no FLOOR neighbours, e.g. the deep inside of a thick wall) and isolated pillars (FLOOR on all four sides — direction sums to zero) keep pure random jitter. All RNG draws go through the global `randi()` / `randf()` so a `seed(N)` ahead of `generate()` makes filler placement deterministic. Out-of-grid cells (in the border ring) carry through with negative or out-of-bounds coords — the renderer treats them identically since `world_position = (cell + 0.5 + offset) × CELL_SIZE` handles any integer cell coord.

**Walkable-area scenery placement.** `_place_scenery()` runs IMMEDIATELY BEFORE `_place_fillers()` — i.e. last among walkable-area passes, so every other system's cells are known and excluded. No-op when `scenery_spawns_pool` is empty. For each `ScenerySpawn` the placer runs up to three additive passes: `_place_scenery_dead_ends(spawn)` walks every dead-end cell and rolls `dead_end_chance` per cell; `_place_scenery_corridors(spawn, segments)` rolls `corridor_segment_chance` per segment from `_detect_corridor_segments()` (reused from the trap pass) and fills [corridor_coverage_min, corridor_coverage_max]% of the segment's eligible cells; `_place_scenery_rooms(spawn)` rolls `room_chance` per `_room_rects` entry and fills [room_coverage_min, room_coverage_max]% of the room's eligible cells. Coverage rolls go through `_place_scenery_in_cells(spawn, pool, target_count)` which shuffles, tries each cell, and graceful-degrades `min_distance_to_same` by 1 down to 0 until the target count is hit or the pool is exhausted. `_cell_eligible_for_scenery(pos, spawn, plate_cells)` is the unified exclusion filter: rejects WALL cells, cells with any `object` / `trap` / `spinner` / `teleporter` / `scenery` already placed, and projectile-trap pressure-plate cells (gathered once via `_gather_plate_cells()` and threaded through every pass — a flower or tree on the plate decal would fight the trigger art and mimic the "item on plate disables trap" rule); additionally for non-walkable scenery (a tree) rejects entrance / exit / floor-item cells AND every cell in `_projectile_path_cells` (a tree on a launcher's firing line would block the corridor / room the projectile crosses, killing the trap's threat zone and stranding the player behind the tree). `_try_commit_scenery_at(spawn, pos)` is the commit path: rolls `density = spawn.sample_density(randi())`; for non-walkable scenery snapshots reachability via `_bfs_walkable_from(entrance_pos)` BEFORE setting the cell's first SceneryInstance, then re-validates via `_placement_preserves_reachability(pos, before)` and rolls back the cell.scenery slot if the placement strands a previously-reachable cell — same BFS guard chests + doors already use. Once the FIRST sprite is committed (and cell.scenery flipped), `density - 1` additional SceneryInstance entries are appended to the flat `scenery` list with their own jitter offsets (`_sample_scenery_offset(spawn)`) and scales (`spawn.sample_scale(randf())`) — adding more sprites can't change reachability since the cell is already blocked. `min_distance_to_same` is measured CELL TO CELL (not sprite to sprite) and is cross-pass: the same SceneryData's dead-end / corridor / room placements all count toward each other; cross-type (trees vs flowers) doesn't constrain.

### DungeonView.gd
**Type:** Node3D (attached to the DungeonView scene root)
**Purpose:** Renders the dungeon in 3D. Builds flat quad meshes (walls, floors, ceilings) from the grid data, applies biome textures with optional triplanar mapping and normal maps, spawns Sprite3D billboards for items (under `ItemsRoot`), cell-bound objects like chests and levers (under `ObjectsRoot`), edge-bound doors (under `DoorsRoot`), wall-mounted decorations (under `WallDecorationsRoot`), and floor traps (under `TrapsRoot` — see below). **Texture selection (Phase 4 polish):** each floor cell is classified via `LevelGenerator.classify_cell` (Corridor / Room / Dead End) and the renderer asks `BiomeTextureEntry.pick_for(biome.<surface>_textures, classification, cell_pos, history)` for an albedo entry — the deterministic position-hash pick keeps the same cell looking identical across mesh rebuilds, save/load, and seed replays. `_build_mesh` keeps three per-surface history dicts (wall / floor / ceiling) — `entry → Array[Vector2i]` of cells already using that entry — and appends after each pick so the picker can enforce `min_distance_to_same` constraints. A wall between a corridor cell and a room cell renders as two separate quads (one drawn from each floor cell) so each side inherits its host cell's classification — the corridor side and the room side can use different art without any extra book-keeping. Wall picks are per-face (via `LevelGenerator.classify_wall_face`) so a dead-end cell's BACK wall can pull from `PLACEMENT_DEAD_END` entries while the two side walls fall back to `PLACEMENT_CORRIDOR` — a "big tree at the end of the tunnel" texture appears once in front of the player, not wrapping the cell on three sides. Within one classification all faces of a cell still resolve to the same entry (same hash, same matching set), so coherence inside a room or corridor is preserved. Materials are cached per `BiomeTextureEntry` in `_material_cache` (cleared on each `_build_mesh`) so each unique texture variant has exactly one `StandardMaterial3D` instance shared across every quad that resolves to it, instead of one per quad as before. Cell-object Sprite3Ds carry a child `Area3D` with a box collider and metadata pointing back at the `ObjectInstance`; the renderer reads `instance.get_visual_opened()` (not `instance.opened`) to choose between `closed_sprite` and `opened_sprite` so a `LeverInstance` can mirror its linked door's state. Door rendering is a separate code path: each door is a `Node3D` anchored at the edge midpoint (computed once from `cell_a + cell_b`) and Y-rotated to the corridor axis; it holds a non-billboarded `Sprite3D` (with optional `scale.x` stretch via `ObjectData.world_width` so a square wall texture renders at corridor proportions) and a SIBLING `Area3D` with a box collider (sibling, not child, so the sprite's `scale.x` doesn't deform the collider). The Area3D is built unconditionally — the `interactable` flag now controls Game.gd's response to a click (toggle vs. locked-feedback), not whether the click is detected. Door positions are static — they are never refreshed on movement or turn, so they cannot drift. Also creates a transparent `DungeonDropTarget` overlay on top of the SubViewportContainer for drag-drop and click handling (with the container set to MOUSE_FILTER_IGNORE so it doesn't reject input first). Manages camera position/rotation, SubViewport sizing for portrait/landscape, biome environment (fog, ambient). `rebuild_items()` re-syncs item sprites; `rebuild_objects()` re-syncs cell-object sprites (used when a chest opens, when a lever is pulled, or when a door whose lever mirrors it changes state); `rebuild_doors()` re-syncs door visuals (used when a door is toggled). **Wall decorations** are rendered through a separate path. Two visual modes: **flat** (default) — each placement is a `Node3D` anchored at the wall face midpoint, Y-rotated to match the wall mesh's own rotation so the sprite sits flush against the wall. **Face-camera** (`face_camera = true`) — root anchored at the BOTTOM of the decoration (pinned to the wall surface), and `_process` updates the basis each frame so the sprite faces the player around Y while leaning the top out by `top_tilt_degrees` so the decoration reads as a 3D object you walk around. Static decorations (paintings) use `Sprite3D`; animated ones (torches, lanterns) use `AnimatedSprite3D` with the data's `SpriteFrames`, auto-playing the named `default_animation`. When `WallDecorationData.light_energy > 0`, an `OmniLight3D` is added as a child of the sprite — gives torches a real glow without requiring a per-decoration scene. A small `depth_offset` (default 0.02) pulls the sprite off the wall to prevent Z-fighting with the triplanar wall texture. `_billboard_decorations` is the array of face-camera roots that get updated each frame. Lights with `light_flicker_amount > 0` are tracked in `_flickering_lights` and have their `light_energy` jittered each frame by a multi-octave sine pseudo-noise (three non-commensurate frequencies summed to roughly `[-1, 1]`); a per-placement random phase decorrelates the array so torches never flicker in unison. `shake_camera()` is the brief jolt fired on wall bumps.
**Key exports:** show_ceiling, camera_eye_height, wall_height, biome, fov, viewport_ratio_portrait, viewport_ratio_landscape
**Public references:** drop_target (DungeonDropTarget)
**Scenery rendering.** `_build_scenery()` iterates `generator.scenery` (the flat list `_place_scenery` populates) and emits one `Sprite3D` per `SceneryInstance` under `SceneryRoot`. Same Sprite3D pattern as objects/items/fillers: `BILLBOARD_FIXED_Y`, NEAREST filter, `ALPHA_CUT_DISCARD`, `pixel_size = (data.world_height * inst.scale) / texture_height` so per-sprite scale variance ("this tree is a bit smaller") changes the on-screen size without re-importing the texture. No Area3D — scenery is never clickable. `_scenery_position(inst)` combines cell centre + the player-facing lean offset + the per-sprite sub-cell jitter (`inst.cell_offset × CELL_SIZE`), so multi-sprite cells (`density > 1`) produce N sprites scattered inside the same tile while all leaning together as the player turns. `_scenery_sprites: Dictionary[SceneryInstance → Sprite3D]` is the per-instance lookup used by `_refresh_scenery_positions()` — keyed by instance (not cell) because a multi-sprite cell holds several Sprite3Ds at the same cell coord. The refresh re-applies the lean on player turn (called from `set_initial_facing` and `rotate_camera_to` — same wiring as `_refresh_object_positions` for chests). Movement does NOT refresh scenery positions: the lean axis is tied to facing, and refreshing on move would snap the sprite mid-step.

**Key methods:** setup(gen), rebuild_items(), rebuild_objects(), rebuild_doors() (also cascades to rebuild_wall_switches() so linked switch sprites + hide_when_active gating stay in lockstep with door state), rebuild_wall_switches() (re-renders every WallSwitchInstance in `generator.wall_switches` — sprite swap + click Area3D + the hide_when_active vanish path), rebuild_traps(), rebuild_projectile_traps() (Phase 8 Task 3 Subtask C — re-renders all wall-mounted launcher Sprite3Ds), rebuild_teleporters() (Phase 15 Task 6 — re-renders the floor decals + lights for every TeleporterInstance), update_trap_visual(trap: TrapInstance) (cheap per-tick path — flips the trap's spike subtree visible/hidden without rebuilding), spawn_projectile_visual(proj) / update_projectile_visual(proj) / despawn_projectile_visual(proj) (Phase 8 Task 3 Subtask C2 — Game.gd calls these on TIMED rollover / every frame in flight / on IMPACT to lifecycle the per-projectile Sprite3D), move_camera_to(grid_pos, facing), rotate_camera_to(turn_right), set_initial_facing(facing), snap_camera_to(grid_pos, facing) (Phase 15 Task 6 — hard-snap variant used by the teleporter warp; kills any in-flight `_move_tween` and routes through `set_initial_facing` so every per-cell visual recalibrates to the new cell), fade_to_black(duration = 0.18) → Signal / fade_from_black(duration = 0.18) → Signal (Phase 15 Task 6 — overlay-fade helpers used by the teleporter warp; return `Tween.finished` so callers can `await` them; lazy-initialise the ColorRect on `viewport_container`), shake_camera(magnitude = 1.0) — magnitude scales the jolt; wall bumps use the default, locked-door click feedback passes ~0.4 for a softer hit, trap-damage feedback passes 0.7. `shake_camera` kills the in-flight movement tween (`_move_tween`, tracked by `move_camera_to`) and snaps the camera to the canonical grid-cell position before starting its animation. The kill is defensive — the trap path now defers its activation by 0.13s so the move tween has visibly completed before the shake fires, but other future damage sources that don't defer would otherwise see the same "shake pulls camera back to mid-move position" bug.

**Hidden door + wall switch rendering.** When a placed door's `data.appears_as_wall` is true, `_build_doors` routes that door to `_make_hidden_door_node` instead of the regular Sprite3D builder. The closed-state visual is two coplanar MeshInstance3D wall quads (one for each side of the edge, opposite normals via 180° Y-rotation on the flipped quad) sharing a single material picked deterministically via `BiomeTextureEntry.pick_for` against `door.cell_a` — so both faces of the panel match (a mismatched pair would betray the secret). The material is the same StandardMaterial3D the cell-wall pass uses (drawn from `_material_for_entry`), so the panel is pixel-indistinguishable from any other corridor wall. The opened state renders NOTHING — a truly empty corridor opening; the map mirrors this (closed = wall line, open = no edge). No Area3D is built for hidden doors; the panel is non-clickable, and the paired WallSwitchInstance is the only interaction surface.

Wall switches render under their own `_wall_switches_root` Node3D. Each `WallSwitchInstance` (whose `should_hide()` is false — `hide_when_active = true` + on-door + door open all together) becomes a Node3D positioned at the wall face midpoint (`view_cell + view_side` offset by half a cell, then `along_offset` along the wall's tangent in WORLD UNITS; tangent is +X for NORTH/SOUTH walls, +Z for EAST/WEST walls), Y-rotated so a `Sprite3D` (default-facing -Z) faces back at the player who stands in `view_cell`. Sprite swap (closed/opened) reads from `WallSwitchInstance.get_visual_opened()` (= any linked door open), same convention LeverInstance uses. A child Area3D + box collider carries the click pickability; `set_meta("object_instance", sw)` lets the DungeonDropTarget raycast resolve back to the switch on click. `_WALL_SWITCH_DEPTH_BIAS = 0.02` floats the sprite slightly in front of the wall to avoid Z-fighting with the triplanar wall texture beneath.

**On-tile item shift (Phase 7 polish 2):** when the player stands on a cell that holds items, the stack slides forward along the player's facing direction by `ITEM_ON_TILE_FORWARD_OFFSET` (1.5 world units) so the items appear at the bottom of the view instead of directly under the camera (where they'd be off-screen given the eye height vs item world_height). Items on every OTHER cell stay centred so a pile across the corridor reads as one cluster from a distance. `_item_sprites: Dictionary[Vector2i → Array[Sprite3D]]` is the lookup the refresh uses (populated by `_build_items`, cleared on rebuild). `_item_world_position(grid_pos, stack_index, inst)` is the pure positioning helper — checks `grid_pos == _current_grid_pos` to decide whether to apply the shift. `_refresh_item_positions(animated)` runs in `set_initial_facing` (animated = false — initial snap, no camera tween to sync with), `move_camera_to` (animated = true), and `rotate_camera_to` (animated = true) so the shift tracks both cell-change and turn. Unlike chests, items DO refresh on cell-change (not just on turn) because the shift is keyed to cell-residency, not the facing axis. When animated, position changes are tweened over 0.12s in parallel with the camera tween so items glide between centred and shifted positions instead of popping (early prototype snapped instantly and felt glitchy). `_item_tween` is killed on every refresh so consecutive moves don't fight each other for the sprite's position property — same defensive pattern as `_move_tween` in `move_camera_to`. Sprites that already sit at their target position skip the tween entirely (no-op tweens would waste a slot in the parallel tween group).

**Trap rendering (Phase 8 Task 3 Subtask A):** each `TrapInstance` renders as TWO pieces inside `TrapsRoot`. (1) **Floor decals** for the holes — always visible, drawn from `data.holes_sprite` with alpha-scissor transparency and NEAREST filter, lying flat on the floor at Y = 0.01 to avoid Z-fighting with the floor texture. To keep draw calls cheap when many traps are placed (corridor clusters + room density combined easily produce 50–100 traps per level), every decal across every trap that shares a `holes_sprite` texture renders through a **single batched `MultiMeshInstance3D`** (one per texture). The MultiMesh's mesh is a unit `QuadMesh` shared across all variants — the per-instance transform's scale encodes the hole size. Hundreds of individual `MeshInstance3D` nodes collapse into one draw call per texture. (2) **Per-spike `Sprite3D` billboards** under a "Spikes" `Node3D`, visible only while the trap is EXTENDED. Each spike is its own billboard so the cluster reads as 3D (multiple billboards at different XZ positions parallax against each other as the player moves). Spikes intentionally stay individual nodes — they need FIXED_Y billboarding (which MultiMesh would need a custom shader to replicate) and `Game.gd` toggles their `visible` flag per state, which is cleaner with a per-trap parent. They're also only on-screen while extended, so peak draw-call cost is a fraction of the always-visible decals. The Spikes subtree position is offset by `_trap_spike_offset(trap)` (cell-relative, derived from `data.spike_lean_toward_player` and the player's facing) so designers can push spikes toward the player while the floor holes stay centred on the cell. The offset is refreshed on player turn (`_refresh_trap_spike_positions`) — same trigger as the chest lean, since the lean axis is tied to facing, not position; refreshing on move would visibly snap the spikes mid-step. Holes texture is rendered as a flat decal — drawn from a top-down perspective. Spikes texture is rendered as vertical billboards — drawn as if seen from the side. They are intentionally different art pieces. Floor materials are cached in `_trap_floor_material_cache` (keyed by Texture2D) and reused by the MultiMesh as `material_override`. `_trap_visuals: Dictionary` (TrapInstance → {root, spikes_root, sprites, tween}) is the lookup `update_trap_visual` / `_refresh_trap_spike_positions` use; `root` no longer holds decals (those live in shared MultiMesh nodes), only the spikes subtree. `sprites` is the flat array of per-spike `Sprite3D` children harvested at build time, used by the extend / retract animation. **Extension animation:** when `TrapData.extended_sprite_frame1` AND `extended_sprite_frame2` are both set, `update_trap_visual` plays a 3-step texture-swap animation on every spike billboard (extending: visible+frame1 → frame2 → extended over 2 × `extension_frame_duration`; retracting: frame2 → frame1 → hidden, symmetric). The `tween` slot stores the in-flight `Tween` so a retrigger kills it before starting the new direction. When frames are unset (current default), the visibility flag is flipped instantly — original snappy behaviour.

**Trap audio:** the original design routed TIMED-trap activate / deactivate sounds through a per-instance `AudioStreamPlayer3D` so the player would hear distant traps fading in as they approached. In practice, Godot 4's spatial audio inside a `SubViewport` had inconsistent listener routing — sounds went silent. Replaced with a non-spatial `SoundManager` path gated by `_player_within_trap_hearing(trap)` in Game.gd: if the player is within `data.hearing_distance` world units (Manhattan tiles × CELL_SIZE), the sound plays at full volume; outside, it stays silent. Drops the smooth distance falloff curve in exchange for reliability. Phase 19's audio polish pass can revisit and reintroduce true spatial audio if desired.

**Projectile-trap rendering (Phase 8 Task 3 Subtask C1):** each `ProjectileTrapInstance` renders as a single `Sprite3D` (the launcher mouth) under `ProjectileTrapsRoot`, anchored at the wall-face midpoint with the wall mesh's Y-rotation so the launcher visually faces into the corridor. `pixel_size = launcher_world_height / texture_height` decouples world size from texture pixel size. Three placement-tuning offsets (`launcher_horizontal_offset` along the wall tangent, `launcher_y_offset` from wall midheight, `launcher_depth_offset` away from the wall) let designers position art with off-centre pivots without code changes. The wall tangent is computed as a 90° rotation of `wall_dir` in the XZ plane so a positive `launcher_horizontal_offset` always shifts to the launcher's right as seen from in front of it.

**Plate floor decals (Phase 8 Task 3 Subtask C4):** PRESSURE_PLATE launchers additionally render a flat `MeshInstance3D` `QuadMesh` at the plate cell, lying horizontal at Y = 0.01 above the floor (same Z-fight prevention as spike-trap holes), sized `plate_world_size × CELL_SIZE` (1.0 = fills the cell). Material is shared with spike-trap decals via `_trap_floor_material_cache` (alpha-scissor + NEAREST filter), so a designer reusing the same texture across both systems gets one cached material. Each plate is wrapped in a parent `Node3D` so the inner `MeshInstance3D` keeps a constant -90° X tilt (the "lay flat" rotation) while the parent's Y rotation is tweenable independently. Plates live under `ProjectileTrapsRoot` alongside the launcher Sprite3Ds so a level rebuild frees both together. **Idle / triggered states:** `plate_texture_idle` (the default un-pressed look) renders by default; `plate_texture_triggered` (optional, falls back to idle when null) renders while the plate is held down — by the player standing on the plate cell, or by any item sitting on the plate cell, or (later) by a Phase 10 enemy walking over the plate. Items on the plate also DISABLE the trap (see `Game._check_pressure_plate_trigger`) — dropping an item onto the plate sacrifices the item but turns the plate inert until the item is picked up. `_plate_visuals: Dictionary[ProjectileTrapInstance → {root, mi}]` tracks the parent Node3D and the inner MeshInstance3D for each plate; `_update_plate_visual_states()` runs in `move_camera_to()` (every player step) and in `rebuild_items()` (every item drop/pickup) and diffs against `_plate_triggered_state` so the material is only swapped on actual state CHANGES, not every refresh. **Camera-locked rotation:** every plate's parent `rotation_degrees:y` is tweened alongside the camera in `rotate_camera_to` (same 0.12s curve), so the plate texture stays fixed in screen space across the four cardinal player facings. This lets designers bake shadows / fake depth into the plate art — the texture's "front" is always toward the player, regardless of which direction the player is facing. Initial rotation is snapped (no tween) in `_build_projectile_traps` and `set_initial_facing` so plates render correctly from the very first frame.

**In-flight projectile rendering (Phase 8 Task 3 Subtask C2):** active projectiles render under a separate `ProjectilesRoot` Node3D so launcher churn doesn't disturb the static launcher subtree. One `Sprite3D` per `ProjectileInstance` is created in `spawn_projectile_visual()` (called by Game.gd on TIMED launcher rollover) — `BILLBOARD_FIXED_Y` so it stays upright as the camera turns, NEAREST filtering, ALPHA_CUT_DISCARD. `update_projectile_visual()` runs every frame the projectile is alive: it syncs the sprite's world position from `ProjectileInstance.cell_pos × CELL_SIZE` (Y at corridor mid-height + `projectile_y_offset`) and re-picks the texture against the camera's current XZ-plane forward via `ProjectileInstance.view_for_camera()` — only swaps if the picked view changed since last frame, so most cardinals-only camera frames cost a single dictionary lookup. `despawn_projectile_visual()` frees the Sprite3D on IMPACT. `_projectile_visuals: Dictionary[ProjectileInstance → Sprite3D]` keeps the lookup O(1). `setup()` calls `_clear_projectile_visuals()` to drop any leftover sprites from a previous level so a transition doesn't leak in-flight projectile renderers (the projectile list on `LevelGenerator` is also cleared in `generate()`, so the two stay in sync).

**Spinner rendering (Phase 8 Task 8):** each `SpinnerInstance` renders as a `Node3D` root under `SpinnersRoot`, anchored at the spinner cell, with a flat `MeshInstance3D` `QuadMesh` child laid horizontal (rotated `-PI/2` around X) and textured via `_build_trap_floor_material(decal_sprite)` so spinners share the alpha-scissor + NEAREST-filter material cache with spike-trap decals. The root's `rotation.y` is advanced in `_update_spinner_rotations(delta)` each frame at `spinner.data.visual_rotation_degrees_per_second × delta` (sign matches the instance's resolved direction — CLOCKWISE spinners visually spin clockwise from above), `fmod`'d into [0, 2π) so floating-point precision doesn't drift over a long session. Rotating the ROOT (not the decal) keeps the spin around the world Y axis cleanly separate from the decal's -90° X tilt. `_spinner_visuals: Dictionary[SpinnerInstance → Node3D]` lookup keeps `_update_spinner_rotations` O(N) per frame, where N is the placed spinner count (small — typical biome configs cap at a few dozen). `_make_spinner_decal` returns null when `data.decal_sprite` is unset — designers can ship an "invisible spinner" by leaving the texture empty, in which case the player only feels the spin.

**Teleporter rendering (Phase 15 Task 6):** each `TeleporterInstance` has TWO endpoints, and BOTH render as identical UPRIGHT sprite billboards under `TeleportersRoot` — same `Sprite3D` + `BILLBOARD_FIXED_Y` pattern chests / levers use, so a rune circle reads as a "thing standing in the cell" rather than a floor marking. The visual is a `Node3D` root parked at the endpoint cell with a `Sprite3D` (or `AnimatedSprite3D` when `data.frames` is set) child; `pixel_size = data.world_height / texture_height` decouples world size from texture pixel size, and the sprite position Y = `world_height * 0.5 + y_offset` so its bottom sits at floor level (the `y_offset` knob nudges upward for transparent-padding compensation). When `data.light_energy > 0`, an `OmniLight3D` child is added at the sprite's mid-height so the glow appears to come from the rune. `data.frames` precedence: when set, the renderer uses `AnimatedSprite3D` auto-playing `default_animation`, deriving `pixel_size` from the first frame's height (frames share dimensions by SpriteFrames convention). `_teleporter_visuals: Dictionary[Vector2i (endpoint cell) → entry-dict]` is the lookup — the value is a Dictionary containing `root`, `sprite_node`, `light`, `data`, `pulse_phase`, `base_glow`, `base_alpha`, `base_light_energy` so the per-frame pulse update can modulate everything without re-walking the scene tree. `_make_teleporter_visual(inst, endpoint)` returns `{}` (empty dict, treated as "skip render") when the data has NO sprite, NO frames, AND NO light — a fully-invisible teleporter is valid (the warp still fires because it's keyed off `cell.teleporter`, not the visual) but a wasted Node3D wouldn't help anyone. The fade-to-black / fade-from-black overlay used by the warp lives on DungeonView (single ColorRect parented to `viewport_container`, lazily constructed in `_ensure_fade_overlay`); it's intentionally shared with the planned Phase 15 Task 1 sub-level transitions so both features fade through the same overlay node.

**Outdoor-mode rendering:** when `biome.outdoor_mode = true`, `_build_mesh` skips both the wall-quad pass (corridors are open to the sky) and the ceiling pass (no roof in a forest / on a beach), and `_build_fillers` instead instantiates one `Sprite3D` per entry in `generator.fillers` under `_fillers_root`. Filler sprites use `BILLBOARD_FIXED_Y` so trees stay vertical while rotating to always face the camera horizontally — a flat tree silhouette reads as a cylinder rather than a card without any per-frame update from `_process`. World position is computed from grid coords at draw time: `wx = (cell.x + 0.5 + offset.x) × CELL_SIZE`, `wz = (cell.y + 0.5 + offset.y) × CELL_SIZE`, `wy = effective_height × 0.5 + y_offset` so the bottom sits at floor level. `_build_outdoor_floors` runs between `_build_mesh` and `_build_fillers` and extends floor geometry beyond the walkable area — it iterates every cell in `[-outdoor_floor_extent, grid_width + outdoor_floor_extent) × [-outdoor_floor_extent, grid_height + outdoor_floor_extent)`, skips cells that already have a floor from the main pass (FLOOR / ENTRANCE / EXIT), and emits a horizontal quad textured from `biome.filler_floor_textures` (falls back to `biome.floor_textures` when empty). Without this pass trees float on the sky background and the player loses depth cues; with it, the ground stretches out beneath the trees and fog softens the edge. `_apply_biome_sky` swaps the WorldEnvironment background — `sky_material` wins (wrapped in a new `Sky` resource, `BG_SKY` mode), else `sky_color.a > 0` flips to `BG_COLOR` with that flat colour, else the scene-authored defaults are restored from `_saved_env_background_*` (captured on first call) so a SparseForest blue sky doesn't leak into the next indoor biome.

**Living-energy pulse + lean (Phase 15 Task 6 polish):** `_update_teleporter_pulse(delta)` runs in `_process` each frame and walks `_teleporter_visuals`. For each endpoint it computes `swing = sin(t * pulse_speed + pulse_phase) * pulse_amount` and applies `multiplier = 1 + swing` to the sprite's `modulate.rgb` (glow) AND `modulate.a` (alpha) AND the light's `light_energy` — all three breathe together so the rune reads as a living energy ball. `pulse_phase` is set per-pair at build time as `pair_index * pulse_phase_per_pair`, so both endpoints of one pair stay in sync (one creature, two windows) but consecutive pairs are offset (independent creatures). `pulse_amount = 0` or `pulse_speed = 0` disables the animation cheaply (the loop skips the math). `_refresh_teleporter_positions()` recomputes each root's position via `_teleporter_position(endpoint, data)` whenever the player TURNS (called from `set_initial_facing` and `rotate_camera_to`), applying `data.lean_toward_player` along the player-facing axis — same shape as the chest lean (`_object_position`), including the strafe-doesn't-flip-axis rule, so the rune visually leans toward the camera without snapping mid-step.

### PlayerController.gd
**Type:** Node (attached to the PlayerController node inside DungeonView)
**Purpose:** Handles step-by-step player movement on the grid. Tracks grid position and facing direction. Provides 6 movement functions (forward, backward, strafe left/right, turn left/right). Before moving, checks both that the target cell is unblocked AND that the edge between current and target isn't blocked by a closed door (`LevelGenerator.is_edge_blocked`). Tells DungeonView to tween the camera.
**Key methods:** move_forward(), move_backward(), strafe_left(), strafe_right(), turn_left(play_sound = true), turn_right(play_sound = true) — the optional `play_sound` parameter (default `true`) lets callers suppress the per-turn rustle; Phase 8 Task 8 spinner spins pass `false` so the spinner's own per-90°-turn whoosh isn't doubled by the global turn sound.
**Key state:** grid_pos (Vector2i), facing (Direction enum)

### BiomeData.gd
**Type:** Resource (data only, loaded as .tres files)
**Purpose:** Defines all visual, environmental, level generation, and loot properties of a biome. Holds arrays of `BiomeTextureEntry` for wall/floor/ceiling surfaces (each entry holds an albedo + placement flags + weight + min-distance rules so the renderer picks variants per cell type), fog settings, ambient light settings, triplanar mapping toggles, wall height, all dungeon generation parameters (grid size, maze behavior, corridor width, room placement, entrance/exit rules), and the floor loot pool (Array of LootEntry + min/max items per level). Loaded at runtime and passed to both DungeonView (appearance) and LevelGenerator (generation + item placement).
**Key exports:** wall_textures, floor_textures, ceiling_textures, fog_enabled, fog_color, fog_density, fog_aerial, ambient_color, ambient_energy, use_triplanar, triplanar_sharpness, triplanar_y_offset, grid_width, grid_height, maze_bias, wiggle, corridor_min_width, corridor_max_width, width_change_chance, room_count, room_min_size, room_max_size, entrance_at_dead_end, exit_at_dead_end, min_exit_distance, floor_loot, floor_items_min, floor_items_max, objects, linked_objects, wall_switched_doors, key_door_spawns, trap_spawns, projectile_trap_spawns, spinner_spawns, wall_decorations, secret_wall_spawns, teleporter_spawn, scenery_spawns, move_sounds, outdoor_mode, filler_spawns, filler_floor_textures, outdoor_floor_extent, sky_color, sky_material

**Outdoor mode (`outdoor_mode = true`):** the renderer skips wall geometry entirely and the LevelGenerator seeds billboarded "filler" sprites (trees / rocks / bushes) on every WALL cell + a configurable border ring outside the grid via `filler_spawns`. **Floor extends past the walkable area:** the under-filler floor (and the border ring outside the grid, controlled by `outdoor_floor_extent` in cells) is drawn from `filler_floor_textures` if non-empty, else falls back to `floor_textures` — gives the player a depth reference so trees don't appear to float on the sky. The sky background is overridden per-biome: `sky_material` (a `PanoramaSkyMaterial` / `ProceduralSkyMaterial`) wins if set, else `sky_color` (alpha > 0) as a flat colour, else the WorldEnvironment's scene defaults are restored. Indoor biomes are unaffected — the new fields are no-ops when `outdoor_mode = false`. `wall_decorations`, `projectile_trap_spawns`, and `secret_wall_spawns` are conceptually banned in outdoor biomes (they need wall geometry to attach to) — leave those arrays empty.

### BiomeTextureEntry.gd
**Type:** Resource (data only, used inside `BiomeData.{wall,floor,ceiling}_textures`)
**Purpose:** One entry in a biome's texture pool — holds the `albedo` texture and the rules for where / how often it spawns. Normal maps were intentionally dropped: they don't help the chunky pixel-art look under the ambient-only lighting model, and the original "pair them so they can't desync" motivation goes away once `normal` is gone. The `placement` flag-set scopes the entry to specific cell classifications: a "mossy dead-end" wall variant only spawns on dead-end cells; a "vaulted room ceiling" only on room cells; etc. Reuses the same `PLACEMENT_CORRIDOR / ROOM / DEAD_END / ANY` flag bits as `LootEntry` / `ObjectSpawn` / `WallDecorationSpawn`. `weight` (default 1) drives a deterministic weighted pick across the matching pool — `weight = 0` excludes an entry from rolls (handy for designers temporarily disabling a variant), and if every matching entry has weight 0 the picker falls back to a uniform pick so a quad never goes blank. `min_distance_to_same` (Manhattan tiles, default 0) spreads a variant out so it doesn't cluster — when no entry can satisfy its own constraint at a given cell, the picker relaxes the rule and picks anyway (better a slight cluster than a missing texture). The static `pick_for(entries, classification, cell_pos, placed_history)` filters by classification → distance → weighted hash; the caller passes a `placed_history: Dictionary` (entry → array of `Vector2i`) and appends to it after each pick (`DungeonView._build_mesh` keeps three: wall / floor / ceiling). Same input → same output, so textures don't reshuffle across mesh rebuilds, save/load, or seed replays.
**Key exports:** albedo, placement, weight, min_distance_to_same
**Key constants:** PLACEMENT_CORRIDOR / PLACEMENT_ROOM / PLACEMENT_DEAD_END / PLACEMENT_ANY
**Key methods:** allows(placement_type), static pick_for(entries: Array, classification: int, cell_pos: Vector2i, placed_history: Dictionary = {}) → BiomeTextureEntry

### LootEntry.gd
**Type:** Resource (data only, used inside BiomeData.floor_loot)
**Purpose:** One entry in a biome's floor-loot pool. Defaults: weight 1, placement = all three types, no min distance. `allows(placement_type)` checks one of the constants `PLACEMENT_CORRIDOR / PLACEMENT_ROOM / PLACEMENT_DEAD_END`.
**Key exports:** item, weight, placement, min_distance_to_other_item

### ItemData.gd

### ItemInstance.gd
**Type:** RefCounted (runtime data, not attached to any node)
**Purpose:** A live instance of an item — points at an `ItemData` and tracks per-instance state (`stack_count`, `durability`, `key_id`, `hue_shift` + cached recoloured textures). Stackable items share an instance with `stack_count > 1`; equipment with durability gets one instance per piece. Use `ItemInstance.create(data, count)` to build one. `can_stack_with(other)` checks if two instances can merge — for keys, two instances built from the same key `.tres` but with different `key_id`s do NOT stack (they unlock different doors). `get_key_id()` returns the per-instance `key_id` if non-empty, else falls back to `data.key_id` — auto-generated lock ids land on the instance, designer-baked ones live on the data. `apply_hue_shift(shift: float)` bakes per-pixel hue-rotated copies of `data.icon` and `data.dungeon_sprite` (preserving saturation, value, alpha) and caches them; `get_icon()` / `get_dungeon_sprite()` return the baked texture when present, falling back to `data.*` otherwise. Renderers (`ItemBar` slot button, `DungeonView` floor sprite, `LootPopup` slot icon) call those accessors — multiplicative `modulate` tinting was abandoned because on a strongly-coloured base sprite (e.g. a yellow key) it only produced brightness variations, not real hue differences. `KeyDoorSpawn` placement calls `apply_hue_shift` per pair so keys for different locks but the same `.tres` render in actually different colours.

### ObjectData.gd
**Type:** Resource (data only, loaded as .tres files in `res://assets/objects/`)
**Purpose:** Template for an interactable dungeon object — chests, doors, levers, traps, campfires, decorations. Holds the category, blocks_movement flag, closed/opened sprite textures, world height/width + y-offset + lean-toward-player offset, the `interactable` flag, a `popup_delay`, and three sound/feedback fields (`interact_sound`, `locked_sound`, `locked_message_key`). One `.tres` per object type — multiple chests of the same type share data, only their `ObjectInstance` state differs. `world_width = 0` keeps the texture's natural aspect (chests, small props); `> 0` forces a non-uniform horizontal stretch via `Sprite3D.scale.x` (used by doors so a square wall texture renders at corridor proportions). `interactable = true` (default): clicks toggle state (chest opens, door swings, lever pulls). `interactable = false`: clicks still register, but instead of toggling, the object plays `locked_sound` and the HUD shows a toast built from `locked_message_key` — used for doors that need a lever or key to actually open. The Area3D is built either way so the player gets feedback rather than a silent dead click. `popup_delay` (seconds) holds a beat after a chest flips to its open sprite + plays `interact_sound` before the loot popup appears — 0 = instant, ~0.4 reads as "I opened it, then here's the loot". **Loot is no longer stored here**; it lives on the per-placement `ObjectSpawn.loot_table` so the same chest visual can hold different contents in different biomes.
**Key exports:** name_key, description_key, category, blocks_movement, appears_as_wall (DOOR only — when true, renders as biome wall geometry while closed and as a void while open; the closed_sprite / opened_sprite are ignored and the door is non-clickable, so only a paired WallSwitchInstance can toggle it), hide_when_active (WALL-SWITCH only — when true AND the switch sits on the linked door's panel, the switch + click area vanish once the door opens; turns the puzzle into a one-shot. Switches on real walls (distance > 0) ignore the flag because they have no visual problem to fix when their door activates), closed_sprite, opened_sprite, world_height, world_width, y_offset, lean_toward_player, interactable, popup_delay, interact_sound, locked_sound, locked_message_key
**Key methods:** get_display_name(), get_display_description()

### ObjectInstance.gd
**Type:** RefCounted (runtime data)
**Purpose:** A placed object's runtime state. Holds the `ObjectData` reference, an `opened: bool` flag (chest been looted, door been opened, etc.), an `items: Array[ItemInstance]` for chest contents (rolled once on first open, persists if popup closes mid-take so the player can come back), and a `loot_table: LootTable` reference set by `LevelGenerator` at placement time (copied from the `ObjectSpawn` that placed this instance). `get_visual_opened()` returns `opened` by default — subclasses override it to derive their sprite state from elsewhere (a `LeverInstance` mirrors its linked door's state, for example).

### DoorInstance.gd
**Type:** RefCounted (extends `ObjectInstance`)
**Purpose:** Runtime state for a door placed on the EDGE between two adjacent floor cells. Doors are NEVER stored on a `GridCell` — they live exclusively in `LevelGenerator.doors`. This is structural: the cell-based renderer / movement code cannot see them, so the door cannot be drawn at cell centre or treated as a cell-blocker by mistake. `cell_a` and `cell_b` are stored canonically (smaller cell first under lex ordering — lower x, then lower y) so any pair `(a, b)` and `(b, a)` resolves to the same door. Static helpers `canonical_pair(a, b)` and `edge_key(a, b)` keep dictionary keys order-independent. `axis()` returns `(1,0)` for E-W corridors or `(0,1)` for N-S corridors, derived from the cells. `is_edge_blocked()` is true iff the door currently obstructs movement (`data.blocks_movement` is true AND `opened` is false). `is_door()` returns true; `is_chest()` returns false. **Lever locks (M:N clusters):** `linked_levers: Array` holds back-links to the levers that control this door (populated by `LevelGenerator` for `LinkedObjectSpawn` clusters; empty for decorative/key-locked doors). `lever_logic: int` (enum `LeverLogic { AND = 0, OR = 1 }`) determines how the door evaluates its linked levers: AND requires ALL levers pulled, OR requires ANY one. `is_lever_locked()` returns true when `linked_levers` is non-empty. `compute_lever_opened()` evaluates the door's opened state from the linked levers' pulled states under the configured logic. Lever-locked doors NEVER toggle via direct click — `Game.gd` shows locked/partial feedback instead. **Phase 8 Task 2c — key locks:** `lock_id: String` is set by `LevelGenerator` for KeyDoorSpawn doors (auto-generated unless the spawn's `lock_id_prefix` is set); `unlocked: bool` flips true the first time the player applies the matching key and stays true forever. `is_key_locked()` returns true iff `lock_id` is non-empty AND `unlocked` is false.
**Key fields:** cell_a, cell_b, linked_levers, lever_logic, linked_wall_switches (Array[WallSwitchInstance] — back-link populated by LevelGenerator for `WallSwitchedDoorSpawn` clusters; empty for every other door variant. Used by Game.gd to refresh switch visuals after the door toggles, mirroring the role `linked_levers` plays for lever-pairs.), lock_id, unlocked
**Key static methods:** canonical_pair(a, b), edge_key(a, b), create_door(data, a, b)
**Key methods:** axis(), is_edge_blocked(), is_door(), is_key_locked(), is_lever_locked(), compute_lever_opened()

### WallSwitchInstance.gd
**Type:** RefCounted (extends `ObjectInstance`)
**Purpose:** Runtime state for a wall-mounted switch — sibling to `LeverInstance` but anchored to a wall FACE, not a floor cell. Stored exclusively in `LevelGenerator.wall_switches` (NEVER on `GridCell.object` — same structural rule doors and wall decorations follow, so the cell-based renderer / pathing code stays oblivious to switches). A switch is identified from the player's perspective by `view_cell` (the floor cell the player stands in to see and click the switch), `view_side` (one of `SIDE_NORTH / EAST / SOUTH / WEST` = 0/1/2/3, matching DungeonView's wall-iteration order in `_build_mesh`), and `along_offset` (signed offset in WORLD UNITS along the wall direction — positive = right of centre, negative = left; sampled with random sign at placement). `linked_doors` cross-link with `DoorInstance.linked_wall_switches`; a click flips every linked door's state (TOGGLE semantics — unlike a lever which computes the door from the union of all linked-lever pulled states, a switch click is a direct flip per door). `pulled: bool` mirrors `LeverInstance.pulled` for symmetry; the renderer ignores it and uses `get_visual_opened()` (= any linked door open) for the sprite swap instead — same convention as a real-world light switch where "the light is on" matters more than "the switch is up". `is_on_door()` is true iff `view_cell` is one of the linked door's endpoints AND `view_side` points across the door's edge (switches at `WallSwitchedDoorSpawn.max_wall_distance = 0` always satisfy this). `should_hide()` is true iff `ObjectData.hide_when_active` is on AND `is_on_door()` AND a linked door is currently open — scoped to on-door switches because off-door switches stay anchored to a real wall that doesn't move when the door opens.
**Key fields:** data, view_cell, view_side, along_offset, linked_doors, pulled
**Key constants:** SIDE_NORTH, SIDE_EAST, SIDE_SOUTH, SIDE_WEST, SIDE_DIRS (cardinal Vector2i array)
**Key static methods:** WallSwitchInstance.create_switch(data), WallSwitchInstance.dir_for_side(side) → Vector2i
**Key methods:** is_wall_switch(), toggle(), is_on_door() → bool, get_visual_opened() → bool, should_hide() → bool

### WallSwitchedDoorSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.wall_switched_doors`)
**Purpose:** A biome-level entry that spawns wall-switch ↔ door pairs (sibling to `LinkedObjectSpawn` for levers and `KeyDoorSpawn` for keys). Each entry produces `count_min..count_max` pairs, each one switch wired to one door. The puzzle shape mirrors `LinkedObjectSpawn` (the switch opens its paired door) but the placement math is fundamentally different — the switch lives on a wall FACE, not a floor cell, so it doesn't go through the per-classification candidate buckets `_classify_floor_cells` produces. `min_wall_distance` / `max_wall_distance` are in Manhattan CELLS from a door endpoint; the actual distance for each placement is sampled uniformly across the buckets in `[min, max]` that have at least one valid candidate (empty buckets are skipped rather than stalling generation). Distance 0 means the switch sits ON the door panel itself (view_side points across the door's edge). `along_offset_min` / `along_offset_max` are in WORLD UNITS (consistency with the rest of `ObjectData` — `world_height`, `world_width`, `y_offset`, `lean_toward_player`); the placer rolls an absolute magnitude in `[min, max]` then flips the sign 50/50 so the lateral position scatters left/right. A cell is ~4.6 world units wide so usable absolute values land roughly in 0.0–2.0. `door_must_gate_content` (default false — decorative wall-switched doors are allowed) routes through the same `_door_gates_content` check the lever/key passes use; failed placements roll back the door + switch atomically (no orphan halves). The intended use case is hidden doors: pair a `door_object` with `appears_as_wall = true` (so it renders as a regular wall when closed and disappears when open) with a switch sprite, giving a true secret-passage feel where the switch is the only visible cue.
**Key exports:** switch_object, door_object, count_min, count_max, min_wall_distance, max_wall_distance, along_offset_min, along_offset_max, door_min_distance_to_other_object, door_must_gate_content

### LeverInstance.gd
**Type:** RefCounted (extends `ObjectInstance`)
**Purpose:** Runtime state for a clickable lever. Cell-bound (lives on `GridCell.object` exactly like a chest), but with a side-link `linked_doors: Array` that the lever controls. `pulled: bool` tracks the lever's own state — `toggle()` flips it. `get_visual_opened()` returns `pulled` directly, so the renderer picks `opened_sprite` when pulled and `closed_sprite` when not. When pulled, `Game.gd` recomputes each linked door's `opened` state via `door.compute_lever_opened()`, which evaluates the door's `lever_logic` (AND/OR) across all its linked levers.
**Key fields:** linked_doors, pulled
**Key static methods:** create_lever(data)
**Key methods:** is_lever(), toggle(), get_visual_opened()

### ObjectSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.objects`)
**Purpose:** One entry in a biome's object pool. Each entry says "spawn this `object` between `count_min` and `count_max` times in cells matching `placement` flags, spread as far apart as the geometry allows but at least `min_distance_to_other_object` Manhattan tiles from any already-placed object, and (when chest) populate it from `loot_table`". The same `object` (e.g. `chest_wooden.tres`) can appear in multiple `ObjectSpawn` entries with different `loot_table` references — that's how the same chest visual ends up holding different contents per biome. **Placement strategy:** when `min_distance_to_other_object > 0`, `LevelGenerator` uses *farthest-point insertion* — each new object goes to the candidate cell that maximizes Manhattan distance to the nearest already-placed object (random tie-break). If the best achievable distance is below the configured floor, a `push_warning` fires but placement still succeeds, so the biome stays playable even when the configured minimum is geometrically impossible. When `min_distance_to_other_object == 0`, the placer falls back to legacy random shuffle (designer opted out of spacing). The reachability check snapshots the entrance-reachable set before each placement and rejects candidates that would shrink it, so pre-existing isolated regions don't get blamed on the chest. `placement` flags are honoured strictly. For DOOR-category spawns, only `PLACEMENT_CORRIDOR` is meaningful (doors live on edges between two corridor cells); the placement code skips door spawns that don't include the corridor flag. `must_gate_content` is reserved for Task 2c (locked / keyed / lever-gated doors): when true, placement requires that closing this door alone cuts off at least one chest cell or the exit. For Task 2a (decorative doors) it stays false. Defaults: 1–1 of the object, placement = `Room | Dead End`, no minimum distance, no loot table, `must_gate_content = false`.
**Key exports:** object, count_min, count_max, placement, min_distance_to_other_object, loot_table, must_gate_content
**Key constants:** PLACEMENT_CORRIDOR / PLACEMENT_ROOM / PLACEMENT_DEAD_END / PLACEMENT_ANY / PLACEMENT_DEFAULT
**Key methods:** allows(placement_type)

### LinkedObjectSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.linked_objects`)
**Purpose:** A biome-level entry that spawns M:N lever ↔ door CLUSTERS. `count_min` / `count_max` count CLUSTERS; each cluster produces `levers_per_cluster` levers and `doors_per_cluster` doors, all cross-linked. `lever_logic` (AND = 0, OR = 1) propagates to every door in the cluster and controls how it evaluates its linked levers' pulled states. For each cluster, `LevelGenerator` first places doors (1-wide-corridor edges, same eligibility as decorative doors), then places levers (chest-style flag-based filters via `lever_placement`). Levers are spread via farthest-first heuristic, with one-lever-per-room uniqueness enforced for room cells. Distance concepts: `lever_min_distance_to_other_object` and `door_min_distance_to_other_object` are anti-clustering rules vs. ANY already-placed object (graceful-degrade-by-1); `lever_to_door_min_distance` and `lever_to_door_max_distance` are puzzle-design constraints on the spread between each lever and the NEAREST cluster door endpoint, with graceful degrade (~30 attempts at full distance before relaxing). `lever_to_door_max_distance = -1` means unlimited. `door_must_gate_content` (default false) — when true, at least one door in the cluster must gate something (a chest, lever, key, or exit); if none does, the entire cluster is rolled back atomically. Chain reachability (AND/OR-aware) validates that all levers in the cluster are reachable from entrance after placement. If any part of the cluster fails, the entire cluster (all doors + all levers) is rolled back — no orphan halves.
**Key exports:** lever_object, door_object, count_min, count_max, levers_per_cluster, doors_per_cluster, lever_logic, lever_placement, lever_min_distance_to_other_object, door_min_distance_to_other_object, lever_to_door_min_distance, lever_to_door_max_distance, door_must_gate_content

### KeyDoorSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.key_door_spawns`)
**Purpose:** A biome-level entry that spawns a key-locked DOOR + a matching KEY item as a coherent puzzle unit (Phase 8 Task 2c). For each pair `LevelGenerator` picks a 1-wide-corridor edge for the door (auto-generates a unique `lock_id` from `lock_id_prefix` — empty prefix → `"lock_<index>"`), then picks a key spawn location per the `key_spawn_locations` flag-set. Locations: **Floor** (place key on a chest-style cell, `key_floor_placement` flags filter Corridor / Room / Dead End), **Chest** (append key item to a chain-reachable chest's items array — guaranteed loot, no roll), **Enemy Drop** (reserved for Phase 10 — currently warns and falls through). Multiple flags = pick one per key, fall back to others on failure. Anti-clustering distances mirror LinkedObjectSpawn (`key_min_distance_to_other_object`, `door_min_distance_to_other_object`, graceful-degrade). Puzzle-spread `key_to_door_min_distance` / `key_to_door_max_distance` are HARD bounds (`max = -1` for unlimited). `door_must_gate_content` defaults TRUE — placement rejects locks that gate nothing meaningful (no chest, lever, key, or exit becomes unreachable when this door stays closed). All placements validated by chain reachability v2 (tracks open doors AND collected keys); failures roll back lever, key, and door together — no orphan halves.
When multiple location flags are enabled, the per-pair lottery is **weighted-random**: `floor_weight`, `chest_weight`, `enemy_drop_weight` (default 1 each = even shuffle, original behaviour). Setting `chest_weight = 3, floor_weight = 1` biases ~75% of pairs to try Chest first, falling back to Floor only if no eligible chest fits. Setting any weight to 0 disables that location even if its flag is on. `allow_multiple_keys_per_chest` (default **false**) prevents two keys from landing in the same chest — the placement skips chests that already hold any key item and falls through to the next candidate. Set to true for biomes that want richer "hoard" chests.
**Key constants:** KEY_LOCATION_FLOOR / KEY_LOCATION_CHEST / KEY_LOCATION_ENEMY_DROP / KEY_LOCATION_DEFAULT
**Key exports:** door_object, key_item, count_min, count_max, lock_id_prefix, door_must_gate_content, key_spawn_locations, floor_weight, chest_weight, enemy_drop_weight, allow_multiple_keys_per_chest, key_floor_placement, key_min_distance_to_other_object, door_min_distance_to_other_object, key_to_door_min_distance, key_to_door_max_distance
**Key methods:** allows_location(location_bit) → bool

### SecretWallSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.secret_wall_spawns`)
**Purpose:** Biome-level entry that places "fake walls" on edges between two 1-wide-corridor floor cells. Same edge eligibility as doors (`_candidate_edges_for_secret_wall` mirrors `_candidate_edges_for_door` minus the placement-flag gate — secret walls only ever live on corridor edges). The wall is purely visual: `DungeonView._build_mesh` paints a normal-looking wall quad on the edge from BOTH sides (textures picked from the biome's regular `wall_textures` pool so the secret wall is indistinguishable from any other corridor wall), but movement and chain reachability ignore the edge entirely — the player walks through freely in either direction with no state to toggle. `MapPopup` draws a faint wall LINE on the edge once EITHER endpoint cell is explored — same geometry as a real wall line but at `SECRET_WALL_MAP_ALPHA` (≈ 0.7) of the normal alpha, so an observant player can spot the lighter line while a casual glance reads it as a wall. `MapData.reveal_around` refuses to reveal the cell directly behind a secret wall (and the two diagonals on that side, to prevent a bent-corridor leak) so the corridor continuation stays hidden until the player walks through. `gate_mode` controls the content-gating requirement at placement time: **NONE** = no requirement (the wall can hide nothing — designer's risk); **ANY_CONTENT** = same rule key-locked doors enforce (sealing this edge cuts off at least one chest, lever, key, or exit cell from the entrance) — this is the default; **LOOT_ONLY** = stricter, the gated cell must be a chest or a non-key floor-item cell AND the wall must NOT also gate any progression element (exit, lever, key on floor, key inside a chest). Lets designers ship secret walls as pure side-rewards that never block the main path. Placement runs AFTER `_place_items()` (so LOOT_ONLY can validate against floor items) and excludes edges already used by doors. **Placement strategy:** when `min_distance_to_other_object > 0`, the placer uses *farthest-point insertion* (mirrors the chest path) — each new wall goes to the candidate edge that MAXIMIZES the Manhattan distance from either endpoint to the nearest already-placed cell-object (chest / lever), door endpoint, OR previously-placed secret-wall endpoint. If the best achievable distance is below the configured floor, a `push_warning` fires but placement still succeeds. When `min_distance_to_other_object == 0`, the placer falls back to legacy random shuffle. **Bugfix history:** the original predicate ignored other secret walls entirely (only iterated `cell.object` and `doors`), so two walls could land 1 tile apart no matter how high `min_distance_to_other_object` was set; `_nearest_existing_edge_neighbor_distance` now includes secret walls in the measured set.
**Key exports:** count_min, count_max, gate_mode, min_distance_to_other_object
**Key constants:** GateMode { NONE = 0, ANY_CONTENT = 1, LOOT_ONLY = 2 }

### TrapData.gd
**Type:** Resource (data only, loaded as .tres files in `res://assets/objects/`)
**Purpose:** Template for a passive floor trap (Phase 8 Task 3 — Subtask A). One `.tres` per trap variant (step-trigger spike, timed spike, future fireball / immobilize / alert). Distinct from `ObjectData` because traps never gate placement, never get clicked, and have no opened/closed inventory state — they live on `GridCell.trap` (separate slot from `cell.object`) and render through DungeonView's traps path. **Key methods:** get_display_name(), get_display_description(), is_step(), is_timed()

### TrapInstance.gd
**Type:** RefCounted (runtime data)
**Purpose:** Runtime state for one placed trap. Pure state machine — no node access, no audio, nothing observable beyond `state`, `timer`, `on_cooldown`, `cell`. ### TrapSpawn.gd
**Type:** Resource (data only, used inside `BiomeData.trap_spawns`)
**Purpose:** One entry in a biome's trap pool. Three placement modes that combine additively per spawn (set the fields you want; leave the others at their defaults to disable that mode).

**Scattered (Subtask A — per-cell):** `count_min` / `count_max` traps placed individually with a `min_distance_to_other_trap` preference between them. `placement` flags (Corridor / Room / Dead End, reusing ObjectSpawn's bits) constrain where they may land. Distance is graceful-degrade — relaxes by 1 down to 0 if the constraint can't be satisfied, so a tight biome config still produces SOME traps.

**Corridor clusters (Subtask B1 — per-segment):** when `corridor_segment_chance > 0`, the placer rolls per corridor segment and lays a contiguous run of N trap cells inside chosen segments. A "segment" is a maximal connected component of non-junction corridor cells (junctions = corridor cells with 3+ corridor neighbours are excluded so two corridors meeting at a T don't merge). N is rolled in `[corridor_traps_per_run_min, corridor_traps_per_run_max]`, clamped to the segment's eligible-cell count. Segments shorter than the run min are skipped (silent under-delivery is worse than placing fewer traps). Two skip rules govern cross-segment placement: (1) a segment that already holds traps from a prior spawn's pass is skipped (one spawn per segment so the player reads "this corridor is poisoned with X" rather than a layered hazard); (2) a segment **junction-adjacent** to an already-trapped segment is also skipped — without this, two clusters separated by a non-trappable junction read as one long run with a single safe tile in the middle, forcing more damage than the per-segment max would suggest. The corridor pass requires `placement` to include `PLACEMENT_CORRIDOR`; a non-corridor-flagged spawn still runs the scattered pass on whichever cells it allows but produces no clusters.

**Room density (Subtask B2 — per-room):** when `room_chance > 0`, the placer rolls per room and places N traps where N is `[room_coverage_min_percent, room_coverage_max_percent]` of the room's eligible cell count. Two independent constraints govern the result. `room_min_spacing` is a VISUAL rule — it enforces Manhattan distance between traps inside the same room (cross-spawn — earlier spawns' traps are also respected) so trap art doesn't visibly cluster. `room_max_distance_to_safe_cell` is a GAMEPLAY rule (default `0` = disabled) — when set to N, every walkable cell in or one step outside the room must have a non-trap walkable cell within N Manhattan tiles. Without it, high coverage rolls can leave the player surrounded by traps with no foothold; with it, the placer pre-rejects candidates that would isolate any cell so the player always has a step-to-safety. Both rules degrade gracefully: when they would block the rolled target, the pass places fewer traps and stops. `allow_mixed_room_traps` (default true) controls whether THIS spawn may add traps to a room that already holds traps from another spawn — set false for "this room is one-trap-type only" exclusivity (mirrors the corridor cluster's one-spawn-per-segment rule). The room pass requires `placement` to include `PLACEMENT_ROOM`.

Modes are fully additive. Set `count_min = count_max = 0` to disable scattered; `corridor_segment_chance = 0` to disable corridor; `room_chance = 0` to disable rooms.

**Key exports:** trap, count_min, count_max, placement, min_distance_to_other_trap, corridor_segment_chance, corridor_traps_per_run_min, corridor_traps_per_run_max, room_chance, room_coverage_min_percent, room_coverage_max_percent, room_min_spacing, room_max_distance_to_safe_cell, allow_mixed_room_traps
**Key methods:** allows(placement_type) → bool, uses_corridor_clusters() → bool, uses_room_density() → bool

### ProjectileInstance.gd
**Type:** RefCounted (Phase 8 Task 3 — Subtask C2)
**Purpose:** A projectile in flight. Spawned by `ProjectileTrapInstance.tick()` when the launcher's trigger fires (TIMED rollover, or PRESSURE_PLATE step in C4). Lives in `LevelGenerator.projectiles` (flat list) so `Game._process()` can advance every active projectile each frame without scanning the grid. **Coordinate convention:** `cell_pos: Vector2` is in continuous CELL units (matches `LevelGenerator.grid` indexing) — `cell_pos = (5.5, 7.0)` is the horizontal centre of column 5 exactly on the boundary between rows 6 and 7. `direction: Vector2i` is the cardinal flight direction. Pure state machine — `tick(delta, grid, gw, gh) → Event` (NONE / IMPACT) walks integer cells one-at-a-time along `direction` from current to `cell_pos + direction × speed × delta` so a high-speed projectile still impacts the FIRST wall it meets rather than whichever cell `new_pos` lands in. On IMPACT, `cell_pos` is clamped to the wall's near face — the face on the side the projectile entered from — so the sprite sits on the wall, not inside it. The grid is passed in read-only so unit tests can drive it with a fake grid in pure code, no scene tree needed. `damage_latch: bool` defaults false; defined in C2, wired by Game.gd in C3 to prevent a single projectile from damaging twice. **4-direction sprite picker:** static `view_for_camera(direction, camera_forward_xz) → CameraView` returns FRONT / BACK / LEFT / RIGHT using `dot` (= -1: FRONT, = +1: BACK, perpendicular: LEFT/RIGHT via 2D cross-product sign) — DungeonView calls it each frame against the camera's current forward. Static + pure so the matrix is unit-testable without a scene tree.
**Key fields:** data, cell_pos, direction, damage_latch, launcher (Subtask C4 — back-reference to the firing `ProjectileTrapInstance`; Game.gd reads it on IMPACT to clear the launcher's in_flight lock so PRESSURE_PLATE traps can re-fire)
**Key static methods:** create(data, cell_pos, direction), view_for_camera(direction, camera_forward_xz)
**Key methods:** tick(delta, grid, gw, gh) → Event, consume_damage_for_player(player_cell) → bool (Phase 8 Task 3 Subtask C3 — returns true and sets `damage_latch` atomically when the projectile is on `player_cell` AND the latch is unset AND damage > 0; returns false otherwise. Game.gd polls each frame and applies `_apply_party_damage(data.damage)` on success — one damage per projectile, no double-charge)
**Key enums:** Event { NONE, IMPACT }, CameraView { FRONT, BACK, LEFT, RIGHT }

### SpinnerData.gd
**Type:** Resource (data only, loaded as .tres files in `res://assets/objects/`)
**Purpose:** Template for a spinner (Phase 8 Task 8). A spinner is a floor cell that rotates the player a fixed number of 90° turns when stepped on, disorienting them. One `.tres` per variant. SpinnerData defines the allowed RANGE for the rotation count (`min_spins`/`max_spins`) and a direction policy (`CLOCKWISE`/`COUNTER_CLOCKWISE`/`RANDOM`); each placed `SpinnerInstance` rolls a concrete value once at placement and locks it for life. RANDOM policy means each instance picks CW or CCW independently — different spinners sharing this data may disagree. Visual: floor decal (`decal_sprite`, `decal_world_size`, `y_offset`) that rotates continuously at `visual_rotation_degrees_per_second` so players can spot spinners on the floor. Audio: optional `spin_sound` plays once per 90° turn (falls back to the global turn sound). `spin_step_duration` (default 0.13s) controls how long each chained 90° turn takes — must be ≥ 0.12 (DungeonView's `rotate_camera_to` tween length) so successive tweens don't fight for `camera.rotation_degrees:y`.
**Key exports:** name_key, description_key, min_spins, max_spins, direction, spin_step_duration, decal_sprite, decal_world_size, y_offset, visual_rotation_degrees_per_second, visual_frame_count (0 = smooth continuous spin, default; >0 = stepped "spritesheet" look — decal snaps to N equally-spaced angles per revolution. Pair with a low rate so each tick reads as a deliberate frame.), spin_sound
**Key methods:** get_display_name(), get_display_description()

### TeleporterData.gd
**Type:** Resource (data only, loaded as .tres files in `res://assets/objects/`)
**Purpose:** Template for a teleporter (Phase 15 Task 6). A teleporter is a floor cell that warps the player to its paired partner cell. One `.tres` per variant; all pairs in a biome share the same data (per-pair map glyph hue varies via `TeleporterInstance.pair_index`). Visual: an UPRIGHT pixel-art sprite (`Sprite3D` with `BILLBOARD_FIXED_Y`, matching the chest / lever pattern) — `sprite` for a static texture or `frames` for an `AnimatedSprite3D` auto-playing `default_animation` (preferred when both are set). The renderer derives `pixel_size = world_height / texture_height` so designers control real-world size via `world_height` (default 1.8); `y_offset` nudges the sprite up for art with transparent padding at the bottom (sprite bottom otherwise sits at Y=0 / floor level). Transparency + glow knobs: `alpha` in [0, 1] (default 0.8) sells "magic projection" via the Sprite3D `modulate.a`; `glow_multiplier` in [0, 4] (default 1.5) HDR-boosts the `modulate.rgb` so the WorldEnvironment's Glow pass picks up a bloom around the rune. The sprite uses `ALPHA_CUT_OPAQUE_PREPASS` rather than `ALPHA_CUT_DISCARD` so the texture's transparent BACKGROUND stays crisply cut while the opaque pixels render at the configured alpha — `alpha < 0.5` still produces a visible sprite (the DISCARD threshold would have dropped sub-threshold pixels entirely). **Living-energy pulse** (Phase 15 Task 6 polish): `pulse_amount` in [0, 1] (default 0.5) is the ± swing applied to glow + alpha + light energy each cycle; `pulse_speed` in radians/sec (default 3.0 ≈ one breath per 2 seconds) sets the cycle rate; `pulse_phase_per_pair` offsets consecutive pairs (default 1.6 rad) so two pairs in view don't pulse in lockstep — both endpoints of the SAME pair stay in sync (one creature, two windows). Setting either pulse field to 0 disables the animation. **Lean toward player** (`lean_toward_player`, default 0.0, range 0.0–1.5) shifts the sprite horizontally along the player's current facing axis — same mechanic chests use via `ObjectData.lean_toward_player`; recomputed on player TURN only (NOT on movement) so the rune doesn't snap mid-step. Light: optional warm `OmniLight3D` configured by `light_color` / `light_energy` (set to 0 to skip) / `light_range`, positioned at the sprite's mid-height so the glow appears to come from the rune; its energy pulses in sync with the sprite when pulse is enabled. Audio: `warp_sound` plays once on activation (non-spatial — UI-feeling event); `seal_sound` is reserved for Phase C polish (audible cue when the player walks into a sealed wall).
**Key exports:** name_key, description_key, sprite, frames, world_height, y_offset, alpha, glow_multiplier, pulse_amount, pulse_speed, pulse_phase_per_pair, pulse_frame_count (0 = smooth sine breathing, default; >0 = stepped "spritesheet" look — glow + alpha + light energy snap between N discrete brightness levels with uniform per-frame dwell time via phase quantization), lean_toward_player, light_color, light_energy, light_range, warp_sound, seal_sound
**Key methods:** get_display_name(), get_display_description(), is_animated() → bool (true iff `frames` is set; documents the renderer's frames-over-sprite precedence)

### TeleporterSpawn.gd
**Type:** Resource (data only, used as `BiomeData.teleporter_spawn` — SINGULAR, not an array)
**Purpose:** A biome's teleporter config (Phase 15 Task 6). One teleporter style per biome with two MUTUALLY EXCLUSIVE modes selected by `island_count_max`:
- **Phase A shortcut mode** (`island_count_max <= 1`, the default): places `count_min..count_max` independent pairs at random non-special floor cells; warps are pure shortcuts within a single connected map. Set `count_max = 0` to disable teleporters for the biome entirely.
- **Phase C island topology** (`island_count_max >= 2`): runs FIRST in generation, seals K-1 articulation corridor cells where K is rolled in `[island_count_min, island_count_max]`, then places K-1 teleporter pairs as a spanning tree connecting the K resulting islands. Pair count is DERIVED from K (`count_min/count_max` are ignored). The warp graph becomes the only way to cross island boundaries; chain reachability v3 keeps lever / key / chest validation island-aware. Seal placement constraints: `min_seal_distance_to_entrance_exit` (Manhattan, default 4) keeps the seal away from the start and goal, `min_seal_distance_between_seals` (default 5, ignored at K=2) spreads seals out at K≥3 so K=3 doesn't bunch two walls into a 2-cell stub island, and `min_island_size` (default 8) is the QUALITY floor — the seal picker REJECTS any candidate whose smaller resulting component would be below this count, then prefers candidates with the LARGEST smaller-component size (most balanced split). Without this floor a greedy picker happily seals a 2-cell dead-end stub and the warp lands on nothing for the player to do.
Per-pair geometry constraints (apply in BOTH modes): `min_distance_between_partners` (Manhattan, default 6 — keeps a warp feeling like fast travel rather than a single step), `min_distance_to_other_object` (buffer from chests / levers / doors / traps / spinners / plates / items / entrance / exit, default 2 — used by Phase A only since Phase C runs before all other passes), `min_distance_to_other_teleporter` (cross-pair spacing, default 4). All distance constraints graceful-degrade by 1 down to 0 if no candidate qualifies, mirroring the spinner / trap / item placement pattern.
**Key exports:** data, island_count_min, island_count_max, min_seal_distance_to_entrance_exit, min_seal_distance_between_seals, min_island_size, count_min, count_max, min_distance_between_partners, min_distance_to_other_object, min_distance_to_other_teleporter
**Key methods:** uses_partition() → bool (true iff `island_count_max >= 2`; the placer reads this to dispatch between the partition pipeline and the shortcut pipeline)

### Game.gd
**Type:** Node3D (attached to the Game scene root)
**Purpose:** Main game orchestrator. Loads the biome resource, creates the LevelGenerator (configured from the biome), initializes DungeonView and PlayerController, builds a 3-character placeholder party and binds them to CharacterSlots, wires HUD signals (movement pad, map, pickup prompt, drag-drop targets), and routes keyboard input to the PlayerController. Handles map updates and pickup-prompt updates on every player movement. Handles pickup actions, character item-use (consumes one stack on success, shows a "No effect" toast on rejection), and dungeon drops (drops one item at a time onto the player's current cell, rebuilds Sprite3Ds, refreshes the pickup prompt). On `object_clicked`, dispatches by type: a `DoorInstance` toggles open/closed, plays the interact sound, asks DungeonView to rebuild door visuals, and additionally rebuilds cell-bound objects when the door has linked levers so their sprites update too; a `LeverInstance` toggles its `pulled` state, recomputes each linked door via `compute_lever_opened()`, plays the lever's interact sound AND additionally plays a linked door's `interact_sound` if any door's open/closed state actually changed (so an AND-3 cluster only thunks on the lever pull that resolves the puzzle), then rebuilds both doors and cell-objects; a chest opens (rolls loot the first time, swaps to the opened sprite + plays `interact_sound`, then — on a first open with `ObjectData.popup_delay > 0` — holds that many seconds before opening the loot popup so the open sprite and sound register before the modal covers the view; re-clicking an already-open chest skips the delay); a chest with no remaining loot shows the `ui.feedback.empty_chest` toast instead of the popup, and on a re-click of an already-opened-empty chest also plays `SoundManager.play_negative()` so the click isn't silent (the first open's `interact_sound` already covers the opening case). Loot transfers (single-slot click in `LootPopup` and Take All) play the moved item's `pickup_drop_sound` — one sound for Take All (first item with a sound), and only when something actually transferred (no sound when the bar was full and zero items moved). Every dispatch path also short-circuits if `instance.data.interactable` is false: it routes to `_play_locked_feedback`, which plays `locked_sound` and shows a toast from `locked_message_key` instead of the success path. **Key-locked doors (Phase 8 Task 2c):** `_toggle_door` checks `door.is_key_locked()` BEFORE the locked-feedback branch — if the bar holds an `ItemInstance` whose `get_key_id()` matches the door's `lock_id`, one count is consumed via `ItemBar.remove_one`, the door's `unlocked` flag flips true (sticky), and execution falls through to the normal toggle (which now opens the door). When no matching key is found, the locked-feedback path fires using the door .tres's own `locked_message_key` (designer sets this to the "needs key" string for key-locked variants). `_find_key_slot_for(lock_id)` is the helper that scans the bar. **Item description popup (Phase 7 polish):** subscribes to `ItemBar.slot_clicked` to open `ItemDescriptionPopup` for the clicked slot's `ItemInstance` (no-op for empty slots, toggles closed when the same slot is clicked again), and to `ItemBar.inventory_changed` to close the popup automatically on any inventory mutation so it never displays stale state.
**Trap behaviour (Phase 8 Task 3 Subtask A):** Game.gd owns the per-frame trap tick (`_process(delta)`) — it advances every `TrapInstance.tick(delta)` and reacts to observed events. ACTIVATED on a TIMED trap: `update_trap_visual` flips the spike subtree on, the activate sound plays through SoundManager (non-spatial — see DungeonView's "Trap audio" note) gated by `_player_within_trap_hearing(trap)` so far-off cycles stay silent, and if the player is standing on the trap's cell at that moment damage applies (and the per-extension latch is set true). DEACTIVATED: visual flips off, deactivate sound plays under the same hearing gate for TIMED, unconditionally for STEP since the player was right there. `_on_player_entered_cell()` runs whenever the player's grid_pos changes between input calls and **awaits `_TRAP_ACTIVATION_DELAY` (0.13s — slightly longer than the 0.12s movement tween) before doing anything trap-related**, so the camera has visibly arrived at the cell before the spike pops, the screen flashes, and the shake hits. Without the await, the activation reads as a teleport. After the wait it handles two cases: (1) STEP trap → `on_player_step()`, sets state EXTENDED + applies damage if not on cooldown; (2) TIMED trap currently EXTENDED with latch unset → applies damage once and sets the latch (so walking off-and-back-on within the same up phase doesn't double-charge, and standing through ACTIVATED then walking off and back on doesn't either). Standing through `RETRACTED→EXTENDED` while already on the cell triggers the ACTIVATED branch's damage path; the latch is reset by the state machine on every fresh extension so each up phase damages exactly once. STEP traps' activate/deactivate sounds route through SoundManager (non-spatial) for consistent loudness even at the player's feet. `_apply_party_damage(amount)` is the single damage entry point: damages all 3 party members, fires `DungeonView.shake_camera(0.7)`, calls `Hud.flash_damage()`, plays `AudioConfig.pain_sound`. Future damage sources (combat, status effects) reuse this path so the feel stays consistent. The tick is gated by `_is_world_paused()` belt-and-braces in addition to SceneTree's pause flag — the trap state-machine clock never drifts while a modal is open. `_player_within_trap_hearing(trap)` returns true when the player is within `data.hearing_distance` world units (Manhattan tiles × CELL_SIZE) of the trap's cell.

**Teleporter trigger (Phase 15 Task 6 — Phase A):** `_check_teleporter_trigger(player_cell)` runs LAST in `_on_player_entered_cell` (after spike-trap, plate, spinner branches) so the source cell's other effects resolve before the warp moves the player away. The armed-cell latch `_teleporter_just_arrived_cell` prevents bounce-back: when a warp lands the player on cell X, this is set to X and subsequent cell-entry checks on X return early. Stepping onto any non-teleporter cell clears the latch, so a return step re-arms naturally — same shape as `_spinner_just_triggered_cell`. `_trigger_teleporter(inst, destination)` is the async warp driver: sets `_teleporter_warping` (folded into `_is_world_paused` so input drops mid-warp), plays the warp sound, awaits `DungeonView.fade_to_black()`, snaps player + camera via `_player_controller.grid_pos = destination` + `DungeonView.snap_camera_to(destination, facing)` (which kills any in-flight move tween and routes through `set_initial_facing` to recalibrate every per-cell visual), clears `_spinner_just_triggered_cell` so a spinner on the destination still fires, updates map + pickup prompt, awaits `fade_from_black`, clears the warp flag, then re-fires `_on_player_entered_cell` so spike traps / plates / spinners on the destination still resolve (the teleporter latch keeps the warp itself from re-firing).

**Inputs:** WASD/arrows + Q/E for movement; F to pick up items on the current tile. **World-pause gate (Phase 6 polish):** `_on_move` (movement-pad signals) and `_input` (keyboard) both early-return via `_is_world_paused()` (which reads `get_tree().paused` OR the spinner-spin flag OR the teleporter-warp flag OR the chest-open-beat flag `_chest_opening`) so any modal popup that registered as a pause source — map today, future settings / inventory — automatically suppresses gameplay input without changing this script. `_chest_opening` is set true while a chest's `popup_delay` beat is running and also makes `_open_chest` drop re-clicks on any chest until the loot popup is up.
**Debug keys:** F1 spawns a Health Potion into the item bar; F2 damages every party member by 10 HP for testing heal; F3 reveals the entire map. (All three are gated by world pause alongside movement.)

**Wall switch click:** `_on_object_clicked` dispatches `WallSwitchInstance` to `_toggle_wall_switch`. The switch's own `pulled` flag is flipped (kept for symmetry with `LeverInstance`; the renderer ignores it). Every linked door's `opened` flag is then flipped directly — TOGGLE semantics, unlike a lever which computes the door from the union of all linked-lever pulled states. The switch's `interact_sound` plays immediately, and after `_LEVER_DOOR_SOUND_DELAY` the linked door's `interact_sound` plays too (only when a door's state actually changed — same satisfying cause-and-effect beat the lever pull produces). `_dungeon_view.rebuild_doors()` is the wall-switch refresh entry point — it cascades to `rebuild_wall_switches()` so the switch sprite swap + `hide_when_active` vanish path land in lockstep with the door state. The non-interactable case (`switch.data.interactable = false`) routes to `_play_locked_feedback` like every other object class — reserved for future variants that need a key / quest / charge to operate.

**Spinner trigger (Phase 8 Task 8):** `_on_player_entered_cell` calls `_check_spinner_trigger(player_cell)` after the trap + plate branches. If the player cell holds a spinner AND it isn't the most-recently-triggered cell (`_spinner_just_triggered_cell` armed-cell guard), `_trigger_spinner(spinner)` flips `_spinner_spinning = true` (folded into `_is_world_paused` so player input drops), dispatches `spinner.rotations` 90° turns to PlayerController in the resolved direction (with `play_sound = false` so the global turn sound doesn't double up the spinner's own whoosh), and `await`s `spinner.data.spin_step_duration` (floored at 0.12s so the rotate tween settles between steps) between turns. The chained-spin timer uses `process_always = false` so an opened modal pauses the spin cleanly. The armed-cell latch clears when the player steps to any OTHER cell — step-off-and-back-on re-triggers, but standing-and-turning doesn't.

## HUD Scripts (`res://scripts/hud/`)

### HUD.gd
**Type:** CanvasLayer (attached to the HUD scene root)
**Purpose:** Master layout controller for all UI elements. Detects portrait vs landscape orientation and positions all UI panels accordingly (top bar, party panel, item bar, movement pad, pickup prompt, toast). Calculates safe viewport ratios for tablets (reduces DungeonView size if UI doesn't fit). Applies UI scaling when the viewport ratio hits minimum. Sets `HUDRoot.mouse_filter = IGNORE` so the dungeon view's drop target overlay (one CanvasLayer below) can receive item drops cleanly. Creates `PickupPrompt` and `Toast` programmatically as children of HUDRoot. Wires the map button. Provides setup_dungeon_view(), setup_map(), and `show_toast(translation_key, duration)` for transient feedback. **Pause-source registry (Phase 6 polish):** owns a `_pause_sources: Dictionary` keyed by popup id. Modal popups call `add_pause_source(id)` on open and `remove_pause_source(id)` on close; HUD reflects the set onto `SceneTree.paused` so the dungeon (DungeonView, PlayerController, future enemies / traps / timers / tweens) freezes whenever any modal is open. Closing one popup while another is still open keeps the tree paused. The map wiring lives in `_ready` (connects MapPopup's `pause_requested` / `pause_released` signals); future settings / inventory popups follow the same shape.
**Key exports:** viewport_ratio_portrait, viewport_ratio_landscape, min_viewport_ratio
**Public references:** item_bar, movement_pad, pickup_prompt, toast, loot_popup, item_description_popup, damage_flash, party_panel, map_popup
**Key methods:** show_toast(translation_key, duration), flash_damage() (single-shot red full-rect flash via DamageFlash — fires from Game.gd whenever the party takes damage), add_pause_source(id), remove_pause_source(id), is_world_paused()

### ItemBar.gd
**Type:** Container (attached to the ItemBar node)
**Purpose:** Manages 10 inventory slots displayed as a grid AND owns the player's item-bar inventory model (`Array[ItemInstance]` of size 10). Creates slot panels with styled borders + icon button + stack-count label programmatically. Relayouts as 5×2 grid depending on orientation. Slot sizes scale relative to screen dimensions. `add_item(instance)` auto-stacks onto compatible existing stacks then fills empty slots, returning any leftover that didn't fit. `pickup_from(cell)` drains every stack from a `GridCell` into the bar, leaving any leftover stacks on the cell.
**Key signals:** slot_clicked(index), inventory_changed
**Key methods:** add_item(instance) → leftover ItemInstance, pickup_from(cell) → int (total individual items transferred — `0` distinguishes "nothing fit" from a partial pickup), would_fit_all(items) → bool (dry-run for "Take All"), get_slot(index), set_slot(index, instance), clear_slot(index), remove_one(index), relayout(available_width) → Vector2

### PartyPanel.gd
**Type:** HBoxContainer (attached to the PartyPanel node)
**Purpose:** Holds references to the 3 CharacterSlot instances. Provides get_slot(index) to access individual character slots.

### CharacterSlot.gd
**Type:** BoxContainer (attached to each CharacterSlot scene root)
**Purpose:** Displays one party member's info: portrait (in a bordered frame), HP bar (red), MP bar (blue), name label, and 3 action buttons (Attack ⚔, Spell ✦, Defense 🛡). All sizes scale relative to screen dimensions with portrait/landscape adjustments. `bind(character)` connects to a `Character` resource and refreshes the bars whenever the character changes; `_can_drop_data` / `_drop_data` accept dragged `ItemSlotButton` payloads on the portrait/bars/name/gaps (action buttons stay non-droppable), run the effect via `Character.apply_item`, and emit `item_consumed(slot_index)` on success or `item_rejected(slot_index)` if the effect would be wasted.
**Key signals:** portrait_clicked, attack_pressed, spell_pressed, defense_pressed, item_consumed(slot_index), item_rejected(slot_index)
**Key methods:** bind(character), set_hp(current, max), set_mp(current, max), set_portrait(texture), set_character_name(name)

### MovementPad.gd
**Type:** GridContainer (attached to the MovementPad node, columns=3)
**Purpose:** 6 directional buttons arranged in a 2×3 grid. Button sizes scale relative to screen short side. Emits signals: forward_pressed, backward_pressed, turn_left_pressed, turn_right_pressed, strafe_left_pressed, strafe_right_pressed.

### PickupPrompt.gd
**Type:** Button (created programmatically by `Hud.gd` as a child of HUDRoot)
**Purpose:** Floating "Pick up (N)" button that appears when the player stands on a tile with items. `set_count(n)` updates the visible count and shows/hides the button. `flash_bar_full()` temporarily replaces the label with the localized "bag full" message for ~1.5 s when a pickup attempt fails because the inventory is full. ### MapPopup.gd
**Type:** Control (attached to the MapPopup scene root)
**Purpose:** Full-screen map overlay. Draws the dungeon map using Godot's 2D draw functions on a Control node. Shows explored floor tiles as shaded rectangles, walls as lines, the exit as a green diamond, the player as a blinking red arrow, any explored objects as markers (chests = brown filled square; opened chests = outline-only so already-looted ones are visually distinct; levers = small slate-toned diamond, filled when the linked door is closed and outline-only when open), spinners (Phase 8 Task 8 — small purple swirl arc with a comma-tail tip, sweep direction matches the instance's resolved CW/CCW; gated by the `debug_show_spinners` export, mirroring `debug_show_traps` / `debug_show_projectile_traps`), teleporters (Phase 15 Task 6 — filled circle with a darker outline ring and a small centre dot; hue is rotated per `TeleporterInstance.pair_index` modulo `_TELEPORTER_HUE_COUNT = 8` so the two endpoints of a pair share an identical colour and the player can tell at a glance which two cells link; gated by `debug_show_teleporters` which defaults to true since the glyph is meant to be player-facing, not debug-only), and any explored doors as thin slabs perpendicular to the corridor at the cell boundary (filled when the door currently blocks; outline-only when open). Door slabs are only drawn when both endpoint cells have been explored, so they don't leak fog-of-war info about unvisited corridors. **Hidden doors (`ObjectData.appears_as_wall = true`)** are explicitly skipped by the slab pass and rendered by a separate pass: when closed they draw as a regular wall LINE on the edge between cell_a and cell_b (same geometry the cell-wall loop produces for real walls — same colour, same width), so the panel reads as a real wall on the map; when open they draw nothing at all (a true secret passage on the map too). **Wall switches** render after the door / hidden-door passes as a short tick mark crossing the wall edge at right angles — brown when no linked door is open, blue when any linked door is open. The tick's centre follows `WallSwitchInstance.along_offset` (converted from world units to map pixels via `_DUNGEON_CELL_SIZE = 4.6`). Only drawn when the switch's `view_cell` is explored and `should_hide()` is false, so on-door switches with `hide_when_active = true` disappear from the map after their door opens, mirroring the 3D view. **Non-walkable scenery (trees)** is rendered as wall — the cell's floor rect is skipped (parchment background shows through, matching the visual the player sees for real walls) and `_has_wall(x, y)` returns true for the cell so neighbouring walkable floor cells draw a wall line on their shared border. Walkable scenery (flowers) gets no map marker — the player can step through it, so it shouldn't read as a barrier on the map. Handles open/close (with a page-flip-style scale + tilt + fade animation that pairs with the `map_open` / `map_close` SFX), blink timer, and layout for portrait/landscape. Spamming the map button is safe — an in-flight animation is killed and the transform reset before a new one starts. **Debug toggle `debug_show_traps`** (off by default) draws a small upward-pointing triangle on every explored trap cell — red for STEP, orange for TIMED. Used to validate Phase 8 Task 3 trap placement; flip on in the MapPopup scene's Inspector and reload. **Debug toggle `debug_show_projectile_traps`** (off by default) draws a small cyan arrow on the WALL EDGE between every explored launcher's host cell and the wall it's mounted on, pointing in the projectile's fire direction (= -wall_dir). Drawn on the wall edge rather than inside the cell so the marker reads as "the launcher is on this wall" rather than "the launcher is on the floor". Subtask C4 adds: PRESSURE_PLATE launchers ALSO render a small filled cyan square on their plate cell when explored — same tint as the launcher arrow so the developer reads them as a paired trigger + launcher. Used to validate Subtask C placement (escape distance, fire direction toward junctions, no shared wall faces with decorations, plate distance bounds).
**Key exports:** debug_reveal_all (reveals entire map for testing), debug_show_traps (draws spike-trap markers), debug_show_projectile_traps (draws projectile-launcher arrows), debug_show_spinners (draws spinner swirl glyphs), debug_show_teleporters (draws teleporter pair-colour circles — defaults true)
**Key signals:** pause_requested, pause_released — emitted on open / fully-closed so HUD can register / release the map's pause source. Future modal popups (settings, inventory) should expose the same signal shape so HUD's pause-source set composes correctly.
**Key methods:** setup(gen, map_data), open(), close(), is_open() (true while visible — including the close-animation tail), update_player(pos, facing), redraw() (force a redraw of the map after external state changes — used by F3 debug reveal)
**Process mode:** `PROCESS_MODE_ALWAYS` (set in `_ready`) so the popup's open / close tween, blink `_process`, and ✕ button keep working while the SceneTree is paused — MapPopup is what *causes* the pause, after all. Children inherit the mode automatically.
